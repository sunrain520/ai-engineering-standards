# 同类规范文档调研与借鉴

## 一、调研结论摘要

当前阶段聚焦的是 **输出团队可使用的研发工程规范文档**。

本次调研不是为了优先建设规则同步工具、AI IDE 插件或自动化检查平台，而是为了回答：

```text
团队规范文档应该长什么样
规范文档应该包含哪些内容
规范文档如何同时服务研发、AI 和 Code Review
哪些同类产品的文档结构、规则表达和落地方式值得参考
```

从 GitHub、官方文档、AI 编码工具生态、Code Review 工具、开发者门户和公开社区讨论来看，市场上已经出现了几类相近产品或能力：

1. **AI Agent 规则文件体系**：AGENTS.md、CLAUDE.md、Cursor Rules、Copilot Instructions、Cline Rules、Windsurf Rules、Continue Rules。
2. **规则同步与管理工具**：RuleSync、AgentsMesh、AgentLint、AI Coding Rules Directory。
3. **规格驱动开发工具**：GitHub Spec Kit。
4. **AI Code Review 工具**：Greptile、CodeRabbit、Qodo Merge / PR-Agent。
5. **工程规范产品化 / Golden Path**：Backstage、Spotify Soundcheck、Golden Paths。
6. **规范即代码 / 自动检查工具**：Semgrep、OpenRewrite、ESLint Custom Rules、ArchUnit。

这些产品共同说明一个趋势：

> **AI 辅助研发正在从“写 Prompt”进入“工程上下文、规则治理、工具集成、持续检查”的阶段。**

但对当前项目来说，第一优先级不是做工具，而是先把团队规范文档输出清楚：

```text
真实项目经验
    ↓
规范萃取
    ↓
团队规范文档
    ↓
AI Coding Rules
    ↓
Review 检查
    ↓
Prompt 模板
    ↓
后续再考虑工具化导出和自动检查
```

因此，本调研中的工具类产品主要用于参考它们如何组织规则、表达约束、设计 Checklist、支撑 AI 使用，而不是把当前项目直接扩展成工具平台。

## 二、调研范围说明

本次调研覆盖：

- GitHub 开源项目。
- 官方产品文档。
- AI 编码工具规则体系。
- AI Code Review 工具。
- 工程规范工具化产品。
- Reddit、公开网页索引、新闻与技术文章中的社区反馈。

限制说明：

- 已尝试通过 `xreach` 直接检索 X/Twitter，但连接 `x.com` 多次超时。
- 因此 X/Twitter 侧没有使用直接抓取结果作为主要证据。
- 社媒信号主要参考 Reddit、公开网页索引、新闻页面和搜索结果中可访问的公开内容。

## 三、同类产品与能力分类

### 1. AGENTS.md / OpenAI Codex：跨工具 Agent 指令标准

代表产品：

- AGENTS.md open format
- OpenAI Codex / Codex CLI

相关资料：

- [AGENTS.md open format](https://github.com/openai/agents.md)
- [OpenAI Codex CLI Getting Started](https://help.openai.com/en/articles/11096431-openai-codex-cli-getting-started)
- [Codex AGENTS.md docs](https://github.com/openai/codex/blob/main/docs/agents_md.md)
- [Introducing Codex](https://openai.com/index/introducing-codex/)

核心能力：

- 用 `AGENTS.md` 为 coding agent 提供项目级指令。
- 支持仓库根目录和子目录级指令。
- 支持把代码风格、测试命令、目录约束、禁止事项写入 agent 上下文。
- 正在成为多 AI 编码工具之间的通用格式。

可借鉴点：

1. **把 `AGENTS.md` 作为跨工具最小兼容入口**。
2. **根目录放全局规则，子目录放领域规则**，例如 APP、前端、后端分别有自己的范围规则。
3. **规则应短、硬、可执行**，避免把长篇说明全文塞进 agent 上下文。
4. **区分人读文档和 Agent 规则文件**，README 不应该承载所有 AI 指令。

对本项目的启发：

```text
engineering-standards/
    ↓
生成或维护：
AGENTS.md
.github/copilot-instructions.md
CLAUDE.md
.cursor/rules/*.mdc
.clinerules/*.md
.continue/rules/*.md
.windsurf/rules/*.md
```

建议把 `AGENTS.md` 作为第一版 AI 工具接入的核心目标之一。

### 2. GitHub Copilot Custom Instructions：仓库级与路径级规则

代表产品：

- GitHub Copilot repository custom instructions
- `.github/copilot-instructions.md`
- `.github/instructions/*.instructions.md`

相关资料：

- [Adding repository custom instructions for GitHub Copilot](https://docs.github.com/en/copilot/how-tos/custom-instructions/adding-repository-custom-instructions-for-github-copilot)
- [About customizing GitHub Copilot responses](https://docs.github.com/en/copilot/concepts/about-customizing-github-copilot-chat-responses)

核心能力：

- 仓库级规则放在 `.github/copilot-instructions.md`。
- 路径级规则放在 `.github/instructions/*.instructions.md`。
- 路径级规则支持 `applyTo` glob。
- Copilot Chat 和 Copilot Code Review 可以使用仓库规则。

可借鉴点：

1. **全局规则 + 路径级规则** 的结构非常适合多端规范。
2. 路径级规则可对应：
   - APP 端。
   - PC 端。
   - 前端。
   - 后端。
   - 测试。
   - 发布。
   - 安全。
3. 规则文件要明确“什么时候适用”，不要所有规则常驻上下文。

对本项目的启发：

可以设计一套导出目标：

```text
.github/copilot-instructions.md
.github/instructions/app-client.instructions.md
.github/instructions/frontend.instructions.md
.github/instructions/backend.instructions.md
.github/instructions/testing.instructions.md
.github/instructions/security.instructions.md
```

### 3. Cursor Rules：路径作用域、激活模式和 MDC 规则文件

代表产品：

- Cursor Project Rules
- `.cursor/rules/*.mdc`

相关资料：

- [Cursor Rules](https://docs.cursor.com/en/context)

核心能力：

- 规则存储在 `.cursor/rules`。
- 支持 Project Rules、User Rules、AGENTS.md、旧版 `.cursorrules`。
- 支持 `Always`、`Auto Attached`、`Agent Requested` 等规则激活方式。
- 支持 glob 匹配和按目录作用域加载。

可借鉴点：

1. **规则要拆小**，按技术栈、目录、任务类型拆分。
2. **规则应该像内部文档一样清晰**，而不是抽象口号。
3. **通过 glob 控制规则上下文成本**。
4. 不同目录可以有不同规则，适合 monorepo 或部门级规范仓库。

对本项目的启发：

可以把每份规范文档拆成两层：

```text
人读版：
engineering-standards/01-app-client/02-android-standard.md

AI 执行版：
.cursor/rules/app-android.mdc
```

### 4. Claude Code：CLAUDE.md、Memory、Subagents、Hooks

代表产品：

- Claude Code Memory
- `CLAUDE.md`
- `.claude/agents/`
- Claude Code Hooks

相关资料：

- [Manage Claude's memory](https://docs.claude.com/en/docs/claude-code/memory)
- [Claude Code Subagents](https://docs.claude.com/en/docs/claude-code/sub-agents)

核心能力：

- 支持企业级、项目级、用户级 memory。
- 项目级说明可放在 `./CLAUDE.md` 或 `./.claude/CLAUDE.md`。
- `CLAUDE.md` 支持 `@path/to/file` 导入其他文档。
- 支持 subagent，以不同角色处理代码评审、测试、重构等任务。
- 支持 hooks，把工具执行前后接入流程。

可借鉴点：

1. **分层 Memory 机制**：组织级、项目级、个人级。
2. **通过 import 引用规范文档**，避免复制粘贴造成规则漂移。
3. **把规范萃取、代码评审、测试补齐做成专门 subagent / skill**。
4. **hooks 可以作为后续工具化检查入口**。

对本项目的启发：

后续可以设计：

```text
CLAUDE.md
.claude/agents/standard-extractor.md
.claude/agents/code-reviewer.md
.claude/agents/testing-reviewer.md
.claude/agents/security-reviewer.md
```

### 5. Cline Rules：可切换、可分文件、可条件激活的规则系统

代表产品：

- Cline Rules
- `.clinerules/`

相关资料：

- [Cline Rules](https://docs.cline.bot/customization/cline-rules)
- [Cline Rules enterprise configuration](https://docs.cline.bot/enterprise-solutions/configuration/infrastructure-configuration/rules)

核心能力：

- Workspace rules 放在 `.clinerules/`。
- 支持多个 Markdown 文件。
- 支持全局规则和工作区规则。
- 支持规则开关。
- 支持 YAML frontmatter 的路径条件。
- 能识别 Cursor、Windsurf、AGENTS.md 等其他规则格式。

可借鉴点：

1. **每个规则文件只关注一个主题**，例如 architecture、testing、security。
2. **规则可以被打开或关闭**，适合灰度推广。
3. **条件规则减少噪音**，避免所有规则常驻。
4. **支持跨工具格式识别**，说明规则生态正在走向互通。

对本项目的启发：

可以给每个规则文件增加元数据：

```yaml
---
scope: app-client
paths:
  - "android/**"
  - "ios/**"
severity: must
status: active
---
```

### 6. Windsurf Memories & Rules：记忆与规则分离

代表产品：

- Windsurf Cascade Memories
- `.windsurf/rules/*.md`

相关资料：

- [Windsurf Memories & Rules](https://docs.windsurf.com/windsurf/cascade/memories)

核心能力：

- Memories 自动生成，用于保存会话中发现的有用上下文。
- Rules 手动定义，用于明确约束 AI 行为。
- 支持 global、workspace、system-level rules。
- Workspace rules 位于 `.windsurf/rules/*.md`。
- 支持 `always_on` 和 `model_decision` 激活方式。
- 支持把 `AGENTS.md` 作为规则来源处理。

可借鉴点：

1. **区分“记忆”和“规则”**：
   - 记忆是上下文。
   - 规则是约束。
2. **企业级 system rules** 可作为部门强制规范。
3. **规则激活模式** 可以降低上下文成本。
4. 自动生成记忆不能替代团队确认后的正式规范。

对本项目的启发：

本项目也应区分：

```text
代码事实 / 调研记录 / 临时结论
    ≠
正式规范 / AI 强制规则 / Review Checklist
```

### 8. Aider Conventions：轻量级约定文件和 Repo Map

代表产品：

- Aider
- `CONVENTIONS.md`
- Aider conventions repository
- Aider repo map

相关资料：

- [Aider Specifying coding conventions](https://aider.chat/docs/usage/conventions.html)
- [Aider Repository map](https://aider.chat/docs/repomap.html)
- [Aider Conventions Repository](https://github.com/Aider-AI/conventions)

核心能力：

- 用 `CONVENTIONS.md` 指导 AI 遵守代码约定。
- 支持通过 `/read CONVENTIONS.md` 或 `.aider.conf.yml` 加载。
- Repo map 会提取代码库关键类、函数和调用结构，帮助 AI 理解代码。

可借鉴点：

1. **轻量约定文件适合快速试点**。
2. **规则文件应只读加载**，避免 AI 随意修改规范。
3. **Repo map 思路适合规范萃取 Skill**，先提取代码事实，再生成规则。

对本项目的启发：

规范萃取 Skill 可以采用类似流程：

```text
扫描项目结构
提取关键模块
提取关键调用链
识别正例模式
识别反例模式
生成规范草稿
```

### 9. JetBrains Junie Guidelines：自动生成项目 Guidelines

代表产品：

- JetBrains Junie
- `.junie/guidelines.md`
- Junie GitHub App

相关资料：

- [Junie Guidelines](https://www.jetbrains.com/help/junie/customize-guidelines.html)
- [Junie GitHub App](https://www.jetbrains.com/help/junie/junie-on-github.html)
- [Junie Playbook](https://www.jetbrains.com/guide/ai/article/junie/)

核心能力：

- 项目 guidelines 默认放在 `.junie/guidelines.md`。
- 支持 `AGENTS.md` open format。
- 可以让 Junie 分析项目结构和技术栈后生成 guidelines。
- GitHub App 可在 issue / PR 中触发实现和评审。

可借鉴点：

1. **“让 AI 先探索项目，再生成规范”** 是规范萃取 Skill 的直接参考。
2. Guidelines 可以包含技术栈、测试框架、代码风格、反例。
3. GitHub issue / PR 集成可以作为后续产品化方向。

对本项目的启发：

规范萃取 Skill 应支持：

```text
输入项目路径
    ↓
分析目录、技术栈、测试命令、核心模块
    ↓
输出 guidelines / ai-rules / review-checklist 草稿
```

### 10. GitHub Spec Kit：规格驱动开发和 Constitution

代表产品：

- GitHub Spec Kit
- Spec-Driven Development
- `.specify/memory/constitution.md`
- `/speckit.constitution`
- `/speckit.specify`
- `/speckit.plan`
- `/speckit.tasks`
- `/speckit.implement`

相关资料：

- [GitHub Spec Kit](https://github.com/github/spec-kit)
- [Spec Kit Documentation](https://github.github.com/spec-kit/index.html)
- [Diving Into Spec-Driven Development With GitHub Spec Kit](https://developer.microsoft.com/blog/spec-driven-development-spec-kit)

核心能力：

- 用 CLI 初始化规格驱动开发工作流。
- 用 Constitution 定义项目原则和不可违背规则。
- 用 specify、plan、tasks、implement 拆分 AI 开发流程。
- 支持多个 AI coding agent 集成。

可借鉴点：

1. **Constitution 是非常值得借鉴的概念**，对应我们的“部门级强制架构契约”。
2. **把 AI 开发拆成阶段**：需求澄清、方案、任务、实现、检查。
3. **命令化 / Skill 化** 的形式比普通文档更容易进入 AI 工具。
4. **规范不是背景资料，而是每个阶段都必须引用的约束**。

对本项目的启发：

可以设计本项目自己的命令或 Skill：

```text
/standards.extract     从代码中萃取规范
/standards.rules       生成 AI Coding Rules
/standards.review      生成 Review Checklist
/standards.export      导出到 Cursor / Copilot / Claude / Codex 等格式
/standards.check       检查规则漂移和文档完整性
```

### 11. Kiro / Devin / Factory / Jules：AI 研发平台中的团队知识入口

代表产品：

- Kiro Steering / Specs
- Devin Knowledge / Skills / Playbooks
- Factory AGENTS.md / Custom Droids
- Google Jules AGENTS.md
- OpenHands file-based agents

相关资料：

- [Kiro Steering](https://kiro.dev/docs/steering/)
- [Kiro Get Started](https://kiro.dev/docs/)
- [Devin Knowledge Onboarding](https://docs.devin.ai/onboard-devin/knowledge-onboarding)
- [Devin Skills](https://docs.devin.ai/product-guides/skills)
- [Factory AGENTS.md](https://docs.factory.ai/factory-cli/configuration/agents-md)
- [Factory Custom Droids](https://docs.factory.ai/cli/configuration/custom-droids)
- [Jules Getting Started](https://jules.google/docs/)
- [OpenHands File-Based Agents](https://docs.openhands.dev/sdk/guides/agent-file-based)

核心能力：

- Kiro 用 Steering 文件沉淀 workspace / global / team 级知识，并支持 `product.md`、`tech.md`、`structure.md` 等基础文档。
- Kiro Steering 支持 always、fileMatch、manual 等包含模式，适合把规范按目录和任务场景加载。
- Devin Knowledge 把 code conformance、deployment workflows、PR naming、testing workflows 等团队上下文作为新员工 onboarding 一样交给 AI。
- Devin 会从 `.rules`、`.mdc`、`.cursorrules`、`.windsurf`、`CLAUDE.md`、`AGENTS.md` 等专用文件中拉取知识。
- Factory 明确区分 README 面向人、AGENTS.md 面向 agent，AGENTS.md 负责 build、test、architecture、conventions、domain vocabulary。
- Factory Custom Droids 和 OpenHands file-based agents 说明“专用 agent / 子任务角色”可以用 Markdown 文件定义。
- Jules 自动读取仓库根目录 `AGENTS.md`，用于理解代码和生成更相关的 plan / completion。

可借鉴点：

1. **规范文档应像新人 onboarding 材料一样组织**，让 AI 知道产品、技术栈、目录结构、测试方式和团队禁忌。
2. **基础文档三件套值得借鉴**：`product.md`、`tech.md`、`structure.md`。
3. **规则要区分作用域**：全局规则、端规则、模块规则、路径规则。
4. **规范文档要能被不同 AI 平台识别**，至少要能沉淀为 AI Rules 或 AGENTS.md。
5. **专用角色文档值得保留**，例如规范萃取、代码评审、安全检查、测试补齐都可以有各自的规则文档。

对本项目的启发：

当前阶段可以先输出这些规范文档，而不是立即做平台：

```text
docs/01-版本路线/
    背景和目标.md
    产品定位说明.md
    同类规范文档调研与借鉴.md

engineering-standards/00-global/
    product-context.md
    tech-context.md
    repo-structure-standard.md
    global-ai-rules.md

engineering-standards/08-ai-coding/
    standard-extraction-rules.md
    ai-development-input-standard.md
    ai-review-rules.md
    ai-self-checklist.md
```

### 12. dot-agents / Engram / RuleBox / 社区规则库：团队规则资产管理

代表产品：

- dot-agents
- Engram / Engrams
- RuleBox
- Agent Rules Builder
- Prompt Shelf
- AI agent config registry / community rule registries

相关资料：

- [dot-agents](https://www.dot-agents.com/)
- [Engram Docs](https://docs.engram.host/)
- [Engram Tools](https://engram.tools/en)
- [Engrams Docs](https://engrams.sh/docs/getting-started/)
- [RuleBox](https://www.rulebox.ai/)
- [What Are AI Coding Rules](https://www.agentrulegen.com/guides/what-are-ai-coding-rules)
- [The Prompt Shelf](https://thepromptshelf.dev/)

核心能力：

- 把 CLAUDE.md、AGENTS.md、Cursor Rules、Copilot Instructions 等 agent 配置当成可复用资产管理。
- 解决多个 AI 工具之间规则重复、漂移、不一致的问题。
- 提供规则模板、规则市场、团队共享、持久记忆、规则发现等能力。
- 部分产品强调“团队知识持续积累”，而不是每次会话重新解释项目背景。

可借鉴点：

1. **规范文档要有唯一事实源**，避免多份 AI 规则文件内容漂移。
2. **规则资产要可复用**，例如 APP、前端、后端、测试、安全可以各自形成模板。
3. **团队知识要分层**：稳定规范、临时经验、Review 反馈、AI 出错案例不能混在一起。
4. **规则文档要可发现**，命名、目录和索引要清楚。

## 五、对本项目规范文档输出的设计建议

### 1. 明确“人读版 + AI 执行版 + Review 检查版”三类文档

当前阶段的核心交付应是规范文档，而不是工具生成物。

建议每个技术方向至少输出三类文档：

```text
人读版规范
    用于研发、新人、架构师理解团队标准

AI 执行版规则
    用于 Cursor / Codex / Claude Code / Copilot 等 AI 工具作为上下文

Review 检查版清单
    用于 Code Review 和 AI 自检
```

这三类文档可以来自同一套规范内容，但表达方式不同：

- 人读版要解释背景、架构、边界、正反例。
- AI 执行版要短、硬、明确必须和禁止。
- Review 检查版要可逐条勾选、可定位问题。

建议结构：

```text
engineering-standards/
    00-global/
    01-app-client/
    02-pc-client/
    03-frontend/
    04-backend/
    05-testing/
    06-release/
    07-security/
    08-ai-coding/
    prompts/
```

### 2. 建立统一的规范文档模板

每份端规范建议使用统一结构，便于团队理解、AI 引用和 Review 对齐：

```markdown
# xxx 开发规范

## 1. 适用范围

## 2. 架构目标

## 3. 目录结构

## 4. 分层职责

## 5. 核心开发规则

## 6. 数据流转规范

## 7. 状态 / 异常 / 日志 / 测试规范

## 8. 正例

## 9. 反例

## 10. AI Coding Rules

## 11. Code Review Checklist

## 12. 历史兼容说明
```

这一点可以借鉴 Cline、Cursor、Copilot、Claude Code 的规则文档实践：规则必须具体、可执行、可作用到对应目录或场景。

### 3. 建立规范萃取文档流程

规范萃取 Skill 是本项目区别于普通规范库的关键。

建议 Skill 流程：

```text
1. 读取项目背景和技术栈。
2. 扫描目录结构和核心模块。
3. 识别代表性正例代码。
4. 识别历史兼容和禁止反例。
5. 输出代码事实，不先下结论。
6. 从事实推导规范。
7. 为每条规范补充适用范围、正例、反例、AI 生成要求、Review 检查项。
8. 生成 AI Coding Rules。
9. 生成 Code Review Checklist。
10. 标记哪些规则可工具化。
```

当前阶段产物应优先是：

```text
规范萃取记录
规范草稿
正式规范文档
AI Rules 文档
Review Checklist 文档
正例 / 反例说明
```

### 4. 建立规则元数据意识，但不急于工具化

为了后续导出和检查，可以在规范文档中提前保留规则编号、规则等级和适用范围。

第一版不一定需要独立 YAML，但建议每条重要规则至少写清：

```text
规则编号
规则等级：强制 / 推荐 / 历史兼容 / 禁止
适用范围
规则说明
正例
反例
AI 生成要求
Review 检查项
```

后续如果要工具化，再把这些字段抽成机器可读格式。

示例：

```yaml
id: app-client-ui-no-network
title: UI 层不得直接访问网络
scope: app-client
targets:
  - android
  - ios
severity: must
status: active
source:
  type: extracted
  examples:
    positive:
      - path/to/good/example
    negative:
      - path/to/bad/example
ai_rule: true
review_check: true
tooling:
  static_scan: planned
  ci: planned
```

### 5. 明确 AI Rules 是规范文档的一部分

AI Rules 当前应作为规范文档中的正式章节或独立 Markdown 文件，而不是先做多工具导出。

第一版重点输出：

```text
app-ai-rules.md
frontend-ai-rules.md
backend-ai-rules.md
pc-ai-rules.md
global-ai-rules.md
```

这些文件重点回答：

```text
AI 生成代码前必须检查什么
AI 生成代码时必须遵守什么
AI 不得生成什么
AI 修改完成后必须如何自检
```

后续如果要接入工具，再从这些 AI Rules 生成：

目标导出：

```text
AGENTS.md
CLAUDE.md
.github/copilot-instructions.md
.github/instructions/*.instructions.md
.cursor/rules/*.mdc
.clinerules/*.md
.continue/rules/*.md
.windsurf/rules/*.md
.junie/guidelines.md
```

### 6. 建立 Review Checklist 文档

Review Checklist 当前也应先以 Markdown 形式交付，保证 reviewer 可以马上使用。

每个 Checklist 应满足：

```text
按领域分组
每项可勾选
每项能定位到规范条目
高风险项标记强制
能覆盖 AI 生成代码常见问题
```

后续如果要接入 AI Review 或 PR Bot，再逐步升级为结构化配置。

建议格式：

```yaml
checklist:
  - id: app-kmp-boundary
    title: 可跨端逻辑是否下沉 KMP
    severity: must
    applies_to:
      - app-client
    evidence:
      - changed_files
      - module_path
    failure_examples:
      - Android / iOS 重复实现同一业务规则
```

### 7. 建立规则生命周期

借鉴 Continue Hub、Cline Rules 和 Soundcheck 的做法，建议规则分状态：

```text
draft       草稿规则
pilot       小组试用
recommended 部门推荐
must        部门强制
deprecated  不再推荐
forbidden   禁止模式
```

### 8. 建立“正例 / 反例 / 历史兼容”目录

这是防止 AI 学错历史代码的核心。

建议每个端维护：

```text
examples/
    positive/
    negative/
    legacy-compatible/
```

每个示例必须说明：

```text
业务模块
代码路径
为什么是正例 / 反例
对应规则
AI 生成要求
Review 检查项
```


## 十、结合调研后的完善建议

结合上述同类产品，本项目当前最应该完善的是规范文档本身，而不是提前做复杂工具。

### 1. 增加全局上下文文档

这三类文档能让 AI 和新人先理解“这是一个什么项目、技术环境是什么、文档应该放在哪里”。

### 2. 增加统一规范文档模板

借鉴 Cursor Rules、Copilot Instructions、Cline Rules 的规则拆分方式，建议补充：

### 9. 下一步推荐落地顺序

建议按以下顺序完善：

```text
1. 补齐 00-global 的全局上下文和模板。
2. 补齐 08-ai-coding 的规范萃取方法和 AI 使用规范。
3. 将 APP 端已完成规范按模板补规则编号、等级和适用范围。
4. 按同一模板推进 PC、前端、后端规范。
5. 补正例 / 反例说明。
6. 统一各端 Review Checklist。
7. 再评估是否导出 AGENTS.md、CLAUDE.md、Cursor Rules、Copilot Instructions。
```

最终目标是让团队先拥有一套稳定、清晰、可执行的规范文档，再逐步把这些文档接入 AI 工具和 Review 流程。
