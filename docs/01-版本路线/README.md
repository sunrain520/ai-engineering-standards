# 一、第一版规范定位：从团队优秀实践中沉淀 AI 可执行的研发编码契约

## 当前入口

- `背景和目标.md`：建设背景和目标。
- `产品定位说明.md`：产品定位和最终形态。
- `同类产品调研与借鉴.md`：AI 研发相关产品调研。
- `../brainstorms/2026-05-21-001-project-standard-extractor-requirements.md`：`project-standard-extractor` 需求文档。
- `../plans/2026-05-21-001-feat-project-standard-extractor-plan.md`：第一阶段实施计划。

当前第一阶段的 Skill 源包已迁移到 `skills/project-standard-extractor/`，它作为一个单一 Skill workflow，从真实项目代码中萃取团队级规范文档。

第一版开发规范的定位不是“从零设计一套理想化编码手册”，也不是“把网上通用规范搬进团队”，而是：

> **基于现有优秀代码和真实研发习惯，沉淀一套能被人理解、能被 AI 执行、能被 Code Review 检查、能被工具逐步约束的部门级研发编码契约。**

它的核心目标是让团队在推广 AI 辅助研发时，解决三个问题：

```text
AI 不知道团队代码应该怎么写
AI 不知道代码应该写在哪里
AI 不知道哪些写法在团队内是禁止的
```

因此，第一版规范必须围绕 **AI 可遵循、研发可落地、团队可迭代** 来设计。

---

## 1. 第一版规范不是“百科全书”，而是“最小可执行规范集”

第一版不追求覆盖所有细节，而是优先沉淀最影响代码质量和 AI 生成质量的规则。

第一版重点解决：

```text
1. 目录结构怎么放
2. 模块职责怎么分
3. 分层边界怎么守
4. 命名风格怎么统一
5. 数据模型怎么流转
6. 接口调用怎么封装
7. 异常日志怎么处理
8. 状态管理怎么表达
9. 公共组件怎么复用
10. AI 生成代码有哪些禁止事项
```

暂时不追求：

```text
1. 覆盖所有历史代码写法
2. 统一所有细枝末节风格
3. 一次性解决所有架构债务
4. 把所有团队习惯都文档化
5. 替代代码评审和架构评审
```

第一版应该做到：

> **少而准，强约束，能执行。**

---

## 2. 第一版规范的核心价值

第一版规范要成为 AI 辅助研发的基础上下文。

它不是单纯给人看的文档，而是同时服务四类对象：

| 对象 | 规范价值 |
| --- | --- |
| 研发人员 | 明确团队统一写法，减少沟通成本 |
| 新人 | 快速理解项目结构、分层方式和代码习惯 |
| AI | 按团队架构、目录、命名、模式生成代码 |
| Code Review | 提供统一检查标准，减少主观判断 |

所以第一版规范的价值不是“文档完整”，而是：

```text
让研发知道怎么写
让 AI 知道怎么生成
让 Reviewer 知道怎么检查
让团队知道怎么迭代
```

---

## 3. 第一版规范的设计原则

### 原则一：从现有优秀代码中萃取，不凭空设计

第一版规范必须来自真实项目，而不是抽象理论。

每个端都应该选择当前团队公认质量较高、仍在持续维护的模块作为样本，提炼出团队已经验证过的开发模式。

例如：

```text
APP 端：KMP 共享层、Android BaseVM、iOS ReactorKit、HSDataCenterKit
前端：页面结构、组件拆分、API 封装、状态管理
后端：Controller / Service / Repository 分层、DTO 转换、异常体系
PC 端：平台适配层、公共业务层、系统能力封装
```

第一版规范要表达的是：

> **我们团队当前推荐的写法是什么，而不是行业上可能正确的写法是什么。**

---

### 原则二：只沉淀推荐模式，不把历史包袱标准化

现有代码里一定同时存在优秀模式、历史写法和临时方案。

第一版必须区分：

| 类型 | 处理方式 |
| --- | --- |
| 推荐模式 | 写入规范，作为 AI 和新人默认遵循方式 |
| 兼容模式 | 说明仅用于历史代码，不建议新代码继续使用 |
| 禁止模式 | 明确列入反例，AI 不允许生成 |
| 待定模式 | 暂不进入第一版，后续评审后再决定 |

第一版规范最忌讳的是：

> **因为历史代码中存在某种写法，就把它错误沉淀为团队标准。**

---

### 原则三：面向 AI 执行，而不是只面向人阅读

传统规范经常这样写：

```text
代码应保持清晰，模块应保持解耦，命名应具有语义。
```

这类描述对人有启发，但对 AI 不够有效。

第一版规范应该写成 AI 可执行规则：

```text
新增接口时，Controller 只负责参数接收、参数校验和结果返回。
业务编排必须放在 Application Service。
不得在 Controller 中直接访问 Repository / Mapper。
```

每条核心规则最好包含：

```text
规则说明
适用范围
推荐写法
禁止写法
正例
反例
AI 生成代码要求
Code Review 检查项
```

这样 AI 才能稳定遵循，Reviewer 也能据此检查。

---

### 原则四：先统一强约束，再补充风格细节

第一版优先统一影响架构质量的内容，而不是优先纠结格式风格。

优先级应该是：

```text
P0：架构边界、目录结构、模块职责、数据流转、禁止事项
P1：命名规则、异常日志、测试要求、组件复用
P2：代码风格、注释风格、局部写法偏好
```

第一版最应该先回答这些问题：

```text
这段代码应该放在哪一层？
这个能力是否应该复用已有模块？
这个逻辑是否应该下沉共享层？
这个接口返回值是否应该经过 DTO / Domain / VO 转换？
这个页面是否应该通过统一 State 管理？
这个展业地差异是否应该配置化？
```

这些问题决定 AI 生成代码是否会破坏团队架构。

---

### 原则五：规范必须能被 Code Review 和工具检查

第一版规范不能停留在“倡议”，要逐步变成检查标准。

每条重要规范都应该思考：

```text
人能不能 review？
AI 能不能自检？
CI 能不能部分校验？
Lint 能不能自动检查？
单测能不能覆盖？
```

例如：

| 规范 | 检查方式 |
| --- | --- |
| UI 层不得直接请求网络 | Code Review + 静态扫描 |
| 后端 Controller 不得访问 Mapper | Code Review + ArchUnit |
| 前端页面不得直接裸写 request | ESLint 规则 + Review |
| KMP commonMain 不得依赖平台 UI API | 编译约束 + Review |
| DTO 不得直接进入 UI 层 | Review + 类型边界检查 |

最终目标是：

> **文档定义规则，AI 遵循规则，Review 识别问题，工具逐步兜底。**

---

## 4. 第一版规范的边界

第一版规范主要管“新代码”和“被 AI 修改的代码”。

它不要求一次性重构所有历史代码。

建议明确边界：

```text
1. 新需求代码必须遵守第一版规范。
2. AI 生成代码必须遵守第一版规范。
3. 重大重构代码必须遵守第一版规范。
4. 历史代码暂不强制全部整改。
5. 修改历史模块时，新增部分应尽量按新规范落地。
6. 对历史不规范写法，应标记为反例或历史兼容模式。
```

这样可以避免规范刚发布就遇到巨大阻力。

---

## 5. 第一版规范的交付形态

第一版规范不应该只有一个 Markdown 文档，而应该包含三种形态。

### 1. 人读版规范

用于研发、架构师、新人理解团队标准。

```text
xxx-coding-standard.md
```

内容包括：

```text
架构说明
目录结构
分层职责
命名规则
开发模式
正例反例
Code Review Checklist
```

---

### 2. AI 执行版规则

用于 Cursor、Codex、Claude Code、Copilot、内部 AI 平台等工具。

```text
xxx-ai-rules.md
```

内容应该更短、更硬、更像指令：

```text
你必须……
你不得……
生成代码前必须检查……
生成代码后必须自检……
```

---

### 3. 工具检查版约束

用于逐步自动化落地。

```text
eslint
prettier
checkstyle
ktlint
swiftlint
mypy
unit test
arch test
CI check
```

不是所有规范第一版都要工具化，但要为后续工具化预留方向。

---

## 6. 第一版规范的成功标准

第一版规范是否成功，不看文档页数，而看它能不能提升 AI 研发质量。

可以用以下标准判断：

```text
1. AI 生成代码时，能知道代码应该放在哪个目录。
2. AI 生成代码时，能遵守团队分层架构。
3. AI 不会绕过公共网络、缓存、日志、配置能力。
4. AI 不会重复实现已有模块能力。
5. AI 能按照各端状态管理方式生成代码。
6. AI 能识别哪些逻辑应该放共享层，哪些逻辑应该放平台层。
7. Code Review 可以直接引用规范指出问题。
8. 新人可以通过规范快速理解团队推荐写法。
9. 团队可以持续把 AI 出错案例反向沉淀为新规则。
```

一句话：

> **第一版规范成功的标志，是 AI 生成的代码越来越像团队资深工程师写出来的代码。**

---

## 7. 第一版规范的最终定位表述

可以在文档开头这样写：

```markdown
# 第一版规范定位

本规范是部门级研发工程规范的第一版，主要面向 AI 辅助研发场景，同时服务于日常开发、Code Review、新人培养和工程治理。

本规范不是完整的编码百科，也不是对所有历史代码的追认，而是基于当前项目优秀实践沉淀出的最小可执行规范集。

本规范重点定义：

1. 各端工程目录与模块边界；
2. 各端推荐架构与分层职责；
3. 代码生成必须遵守的强约束；
4. 典型正例和禁止反例；
5. AI 生成代码前后的检查要求；
6. Code Review 可执行检查项。

本规范优先约束新需求、新模块、AI 生成代码和重大重构代码。历史代码中的不一致写法不默认视为推荐标准，应通过正例、反例和兼容说明逐步治理。

本规范的目标是让研发人员、AI 工具和 Code Review 使用同一套工程语言，使 AI 能够按照团队既有架构、代码风格和质量要求完成需求开发。
```
