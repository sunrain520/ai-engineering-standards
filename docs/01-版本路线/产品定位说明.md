# 产品定位说明

## 一、产品名称

```text
AI Engineering Standards
```

中文名称：

```text
AI 辅助研发工程规范体系
```

本产品面向部门级研发团队，提供一套可交付、可使用、可迭代的 **规范 + 工具化能力**，用于支撑 AI 辅助研发在真实需求开发中的稳定落地。

## 二、一句话定位

> **AI Engineering Standards 是一套面向 AI 辅助研发的工程规范产品，通过“规范萃取 Skill + 规范结果文档 + AI 使用模板 + Review 检查清单”，把团队真实代码经验转化为人能理解、AI 能执行、Review 能检查、工具能逐步约束的研发工程标准。**

## 三、产品本质

本项目不是单纯的文档仓库，也不是某个技术方向的编码规范集合。

它的本质是：

```text
规范萃取工具
    +
规范结果资产
    +
AI 开发上下文
    +
Review 检查标准
    +
持续迭代机制
```

也就是说，本产品既提供“规范是什么”，也提供“规范如何从真实代码中萃取出来、如何给 AI 使用、如何在 Review 中检查、如何持续更新”的完整方法和工具。

## 四、产品要解决的问题

随着 AI 开始参与需求分析、代码实现、单元测试、代码评审和重构优化，传统只面向人的研发规范已经不够。

当前团队面临的核心问题包括：

### 1. AI 缺少团队级工程上下文

AI 默认掌握的是通用编码知识，但不了解当前团队的真实工程结构、架构分层、模块边界、历史包袱和推荐写法。

典型问题：

```text
代码写错目录
绕过现有公共能力
破坏分层边界
重复实现已有模块
把历史反例当成推荐写法
直接复制不适合当前项目的通用方案
```

### 2. 团队规范分散且不可执行

很多规范存在于资深同学经验中，或者分散在 Code Review、口头约定、历史需求文档和局部 README 中。

这些规范缺少统一表达，导致：

```text
新人学习成本高
不同小组理解不一致
AI 无法稳定遵循
Review 缺少统一依据
规范无法工具化检查
```

### 3. Code Review 标准依赖个人经验

当前 Review 很多时候依赖 reviewer 的个人判断。

这会带来：

```text
同类问题反复出现
不同 reviewer 标准不一致
架构问题发现较晚
AI 生成代码缺少统一自检标准
问题难以沉淀成可复用规则
```

### 4. 历史代码好坏混杂

真实项目中既有优秀实践，也有历史包袱、临时方案和过时写法。

如果 AI 直接学习全量代码，容易出现：

```text
学习到错误模式
复制历史债务
延续不合理分层
扩大重复实现
把兼容写法误判为推荐标准
```

因此，本产品必须把真实代码中的经验进行筛选、分类和结构化表达。

## 五、目标用户

本产品同时服务四类用户。

| 用户 | 核心诉求 | 产品价值 |
| --- | --- | --- |
| 研发人员 | 知道团队推荐写法和禁止写法 | 降低沟通成本，提升代码一致性 |
| 新人 | 快速理解项目结构和研发习惯 | 缩短上手周期，避免踩历史坑 |
| AI 工具 | 获得团队级工程上下文 | 按团队架构和规则生成代码 |
| Reviewer / 架构师 | 统一评审标准 | 提高 Review 质量，减少主观判断 |

同时，本产品也为后续 lint、CI、静态扫描、架构测试等工具化治理提供规则来源。

## 六、产品形态

本产品由三类核心资产组成。

### 1. 规范萃取 Skill

规范萃取 Skill 用于指导 AI 或研发人员从真实项目代码中提炼规范。

第一阶段只保留一个对外 Skill：

```text
project-standard-extractor
```

它不是 APP、前端、后端、行业多个分散入口，而是一个统一 workflow。用户只需要提供一次项目上下文，Skill 内部再拆分 APP / 前端 / 后端 / 行业规范生成、AI Rules、Review Checklist、evidence 和质量评审等任务。

它要回答：

```text
如何选择正例代码
如何识别反例代码
如何区分推荐模式、历史兼容模式和禁止模式
如何从代码事实推导规范
如何把隐性经验转成显性规则
如何生成 AI Coding Rules
如何生成 Code Review Checklist
如何把 AI 出错案例反向沉淀为规则
```

规范萃取 Skill 的核心价值是：

> **让规范不是凭空设计出来的，而是从团队真实优秀实践中萃取出来的。**

Skill 内部采用多 agent 协作：

```text
Intake / Project Profiler / Evidence Collector / Code Facts / Pattern Classifier
    ↓
APP / Frontend / Backend / Industry / AI Rules / Review Checklist / Evidence Writer
    ↓
Evidence Auditor / Team Standard Reviewer / AI Executability Reviewer / Checklist Reviewer / Conflict Reviewer / Industry Risk Reviewer
    ↓
Quality Gate / Merge Coordinator
```

对用户来说是一个 Skill；对执行来说是多个专业 agent 分工。

### 2. 规范结果文档

规范结果文档是萃取后的正式交付物。

包括：

```text
全局研发规范
APP 客户端规范
PC 客户端规范
前端规范
后端规范
测试规范
发布规范
安全规范
AI Coding Rules
Prompt 模板
Code Review Checklist
正例 / 反例说明
规范变更流程
```

规范结果文档的核心价值是：

> **把团队推荐写法、架构边界和质量标准沉淀成可引用的工程契约。**

### 3. AI 使用与检查模板

AI 使用与检查模板用于把规范接入真实 AI 辅助研发流程。

包括：

```text
AI 开发标准输入模板
需求分析 Prompt
代码生成 Prompt
代码 Review Prompt
规范萃取 Prompt
AI 自检清单
Review Checklist
工具化检查建议
```

它的核心价值是：

> **让规范不只停留在文档中，而是能进入 AI 编码、AI 自检和 Code Review 流程。**

## 八、核心使用场景

### 1. 从已有项目萃取规范

适用于各端负责人、架构师或 AI 工具从真实代码中提炼规范。

输入：

```text
项目代码路径
业务模块
正例候选代码
反例候选代码
当前技术栈
团队已有约定
```

输出：

```text
代码事实
推荐模式
禁止模式
历史兼容说明
AI Coding Rules
Review Checklist
正例 / 反例路径
```

### 2. AI 辅助需求开发

适用于研发人员使用 Cursor、Codex、Claude Code、Copilot 或内部 AI 平台完成需求开发。

输入：

```text
需求说明
当前端类型
当前业务模块
相关代码路径
接口文档
设计稿 / 交互说明
全局规范
端规范
模块规范
AI Rules
正例代码
禁止事项
自检清单
```

输出：

```text
需求归属判断
实现方案
修改文件列表
代码变更
测试方案
自检清单
风险说明
```

### 3. Code Review 标准化

适用于 reviewer 对人写代码和 AI 生成代码进行统一检查。

检查内容：

```text
是否破坏分层
是否重复实现已有能力
是否绕过公共网络、缓存、日志、配置体系
是否直接使用 DTO
是否缺少异常兜底
是否缺少日志、埋点和测试
是否硬编码展业地逻辑
是否违反端规范和模块规范
```

输出：

```text
问题定位
违反的规范条目
修复建议
是否需要补充新规则
```

### 4. 规范持续迭代

适用于团队把真实研发过程中的问题反向沉淀到规范仓库。

触发来源：

```text
AI 生成错误代码
Code Review 高频问题
线上问题
新技术栈引入
新业务模块引入
多展业地适配出现新模式
```

输出：

```text
新增规则
新增反例
新增正例
更新 AI Rules
更新 Review Checklist
更新 Prompt 模板
```

## 九、产品边界

### 本产品负责

```text
沉淀团队工程规范
定义 AI 可执行规则
提供规范萃取方法
提供 AI 开发输入模板
提供 Review 检查清单
提供正例 / 反例组织方式
提供工具化检查方向
提供持续迭代机制
```

### 本产品不负责

```text
替代业务项目本身的架构设计
一次性重构所有历史代码
替代研发人员和架构师判断
保证 AI 生成代码完全正确
覆盖所有细枝末节代码风格
在第一版完成全部自动化检查工具
```

本产品的定位是提供工程化约束和上下文，不是替代人类工程判断。

## 十、第一版产品范围

第一版优先交付最小可执行规范集。

重点覆盖：

```text
目录结构
模块职责
分层边界
命名规则
数据流转
接口调用封装
异常和日志
状态管理
公共组件复用
AI 禁止生成项
AI 自检清单
Code Review Checklist
```

第一版暂不追求：

```text
覆盖所有历史代码写法
统一所有细枝末节风格
一次性解决所有架构债务
把所有规则都自动化检查
替代代码评审和架构评审
```

第一版主要约束：

```text
新需求代码
AI 生成代码
被 AI 修改的代码
重大重构代码
新增模块代码
```

历史代码中的不一致写法不默认视为推荐标准，应通过正例、反例和历史兼容说明逐步治理。

推荐仓库结构：

```text
engineering-standards/
├── 00-global/
├── 01-app-client/
├── 02-pc-client/
├── 03-frontend/
├── 04-backend/
├── 05-testing/

```

每个端建议包含：

```text

```

其中：

- `standard.md` 面向研发人员和新人。
- `ai-rules.md` 面向 AI 工具。
- `review-checklist.md` 面向 Code Review。
- `examples/` 用于沉淀正例、反例和历史兼容案例。
- `evidence/` 用于保存真实代码路径、代码事实、正反例和历史兼容证据。
- `prompts/` 用于支撑 AI 开发、规范萃取和代码评审。

## 十二、产品核心原则

### 1. 从真实代码中萃取，不凭空设计

规范必须来自团队真实项目和优秀实践，避免照搬行业通用模板。

### 2. 区分推荐、兼容、禁止和待定

历史代码中存在的写法不自动成为规范。

分类标准：

| 类型 | 处理方式 |
| --- | --- |
| 推荐模式 | 写入规范，作为 AI 和新人默认遵循方式 |
| 历史兼容 | 说明仅用于历史代码，不建议新代码继续使用 |
| 禁止模式 | 明确列入反例，AI 不允许生成 |
| 待定模式 | 暂不进入第一版，评审后再决定 |

### 3. 面向 AI 执行，而不是只面向人阅读

核心规则必须写成明确指令：

```text
你必须……
你不得……
生成代码前必须检查……
生成代码后必须自检……
```

避免只写抽象原则，例如：

```text
代码应保持清晰
模块应保持解耦
命名应具有语义
```

### 4. 先强约束，后风格细节

第一版优先约束：

```text
架构边界
目录结构
模块职责
数据流转
禁止事项
```

其次再补充：

```text
命名规则
异常日志
测试要求
组件复用
代码风格
注释风格
```

### 5. 文档、AI、Review、工具形成闭环

每条重要规范都应该考虑：

```text
人能不能理解
AI 能不能执行
Review 能不能检查
工具能不能逐步校验
```

最终形成：

```text
文档定义规则
AI 遵循规则
Review 识别问题
工具逐步兜底
问题反向沉淀
```

## 十三、成功标准

第一版产品是否成功，不看文档页数，而看是否真实提升 AI 辅助研发质量。

建议用以下标准衡量：

```text
1. AI 能判断代码应该放在哪个目录、模块和分层。
2. AI 能遵守 APP / PC / 前端 / 后端的基本架构规则。
3. AI 能优先复用已有模块、组件、Repository、UseCase。
4. AI 不再随意绕过公共网络、缓存、日志、配置体系。
5. AI 不再把 DTO 直接传递到 UI 层。
6. AI 不再在 UI 层、Controller 层写复杂业务逻辑。
7. AI 能输出修改文件列表、实现方案和自检清单。
8. Code Review 可以直接引用规范指出问题。
9. 新人可以通过规范快速理解团队推荐写法。
10. 团队可以持续把 AI 出错案例沉淀为新规则。
```

## 十四、产品演进方向

### 第一阶段：规范萃取 Skill MVP + 首批规范草稿

目标：

```text
建立目录结构
完成背景目标和产品定位
完成 APP 端初版规范
形成 Prompt 模板
形成 Review Checklist 模板
定义 project-standard-extractor 单一对外 Skill
定义内部多 agent 萃取和评审流程
形成 APP / 前端 / 后端 / 行业规范草稿输出机制
形成 draft / active / pending / conflict / legacy-compatible 状态机制
```

### 第二阶段：规范运营与评审增强

目标：

```text
强化 draft -> active 审核流程
沉淀人工改写后的规范复核能力
增强 evidence 充分性检查
增强规则冲突检测和合并建议
评估是否拆出独立 standard-reviewer Skill
```

### 第三阶段：多端与行业规范补齐

目标：

```text
补齐 PC 客户端规范
补齐测试规范
补齐发布和安全规范
补齐 AI Coding 全局规范
持续补充 APP / 前端 / 后端和行业规范的 evidence
```

### 第四阶段：接入 AI 研发流程

目标：

```text
接入 Cursor / Codex / Claude Code / Copilot / 内部 AI 平台
沉淀标准输入模板
沉淀 AI 自检模板
沉淀 AI Review 模板
在真实需求中试运行
```

### 第五阶段：工具化检查

目标：

```text
将部分规则接入 lint
将部分架构规则接入 CI
将高频问题接入静态扫描
将 Review Checklist 工具化
将规范变更纳入版本管理
```

## 十五、最终定位

本产品最终要交付的不是一批静态 Markdown，而是一套可以被团队长期使用的 AI 辅助研发工程体系。

它包括：

```text
一套规范萃取方法
一套部门级规范资产
一套 AI 可执行规则
一套 Prompt 模板
一套 Review 检查清单
一套持续迭代机制
一套未来工具化检查方向
```

最终目标是：

> **让团队的优秀工程实践可以被新人学习、被 AI 执行、被 Review 检查、被工具约束，并在真实研发过程中持续进化。**
