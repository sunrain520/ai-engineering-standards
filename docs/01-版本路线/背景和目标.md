# 背景与目标

## 一、建设背景

随着团队开始大规模推广 **AI 辅助研发完成需求开发**，AI 已经不再只是用于简单问答、代码片段生成，而是逐步参与到需求分析、代码实现、单元测试、代码评审、重构优化等研发流程中。

当前部门研发团队覆盖多个技术方向，包括：

```text
APP 客户端：Android、iOS、KMP 共享层
PC 客户端：Mac、Windows
前端：H5、Admin
后端：Java、Python
```

各端技术栈复杂，工程结构、架构模式、业务模块、编码习惯也不完全一致。尤其是 APP 客户端已经形成了较复杂的技术体系：

```text
KMP 跨端共享层
Android Jetpack MVVM / HSLoadData / BaseVM
iOS ReactorKit
HSDataCenterKit 数据中台
多展业地配置化与模块化复用架构
```

在这种背景下，如果没有统一的研发规范和 AI 可执行规则，AI 在辅助编码时容易出现以下问题：

```text
1. 不知道代码应该写在哪个目录、哪个模块、哪一层。
2. 不理解团队既有架构，容易破坏分层边界。
3. 不知道哪些能力应该复用，容易重复造轮子。
4. 不知道哪些逻辑应该下沉共享层，导致双端重复实现。
5. 不知道哪些写法是历史包袱，容易把反例当成标准。
6. 不知道团队对异常、日志、状态、DTO、接口、测试的要求。
7. 生成代码后缺少统一自检标准，Code Review 也缺少统一依据。
```

因此，部门需要建设一套统一的 **研发工程规范仓库**，基于现有优秀代码和真实研发习惯，沉淀各端开发规范、架构约束、AI Coding Rules、正反例代码、Prompt 模板和 Code Review Checklist。

这件事的本质不是单纯“写规范文档”，而是建设一套支撑 AI 辅助研发长期落地的 **工程化规范底座**。

## 二、核心问题

当前主要问题可以归纳为四类。

### 1. 团队规范缺失或分散

各小组虽然在实际开发中已经形成了一些隐性约定，但很多规范没有系统沉淀。

例如：

```text
目录结构怎么放
模块职责怎么分
接口如何封装
状态如何管理
异常如何处理
日志如何打印
公共组件如何复用
多展业地差异如何适配
```

这些经验更多依赖资深同学口口相传，不利于新人快速上手，也不利于 AI 稳定遵循。

### 2. AI 缺少团队级上下文

AI 默认只知道通用编码知识，不知道当前团队的真实工程习惯。

例如 APP 端开发中，AI 必须知道：

```text
跨端业务逻辑优先下沉 KMP
Android 使用 ViewModel / BaseVM / HSLoadData
iOS 使用 ReactorKit Action → Mutation → State
数据访问统一走 HSDataCenterKit
DTO 必须通过 Mapper 转换为 Domain Model
展业地差异优先配置化，而不是硬编码 if/else
```

如果这些规则没有结构化沉淀，AI 就很难生成符合团队架构的代码。

### 3. Code Review 标准不统一

当前 Code Review 很多时候依赖 reviewer 的个人经验。

容易出现：

```text
不同 reviewer 标准不一致
同类问题反复出现
规范问题靠口头提醒
AI 生成代码没有统一检查清单
架构问题发现较晚
```

因此需要把 Review 经验沉淀成明确的 Checklist，让人和 AI 都能按同一套标准检查代码。

### 4. 历史代码好坏混杂

现有代码中既有高质量样板，也有历史包袱、临时方案和不推荐继续沿用的写法。

如果直接让 AI 学习全量代码，很容易出现：

```text
把历史写法当成推荐写法
复制过时代码模式
延续不合理分层
重复实现已有能力
继续放大技术债
```

所以第一版规范必须从现有代码中筛选出优秀实践，明确哪些是推荐模式、哪些是禁止反例、哪些只是历史兼容。

## 三、建设目标

本项目的目标是建设部门级研发工程规范仓库：

```text
engineering-standards
```

通过统一规范、统一规则、统一 Prompt、统一 Review 标准，让 AI 能够更高质量地辅助研发完成需求开发。

核心目标可以概括为一句话：

> **让 AI 从“会写代码”升级为“按团队架构、团队习惯和团队质量标准写代码”。**

## 四、具体目标

### 1. 建设统一的部门级规范仓库

建立统一 Git 工程：

```text
engineering-standards
```

用于集中管理：

```text
全局研发规范
APP 客户端规范
PC 客户端规范
前端规范
后端规范
AI Coding Rules
Prompt 模板
Code Review Checklist
正例 / 反例代码
规范变更流程
```

### 2. 从现有优秀代码中萃取真实规范

第一版规范不是从零设计，也不是照搬行业通用规范，而是基于团队真实项目代码进行萃取。

重点识别：

```text
当前团队推荐的目录结构
当前团队推荐的分层方式
当前团队推荐的数据流转方式
当前团队推荐的状态管理方式
当前团队推荐的异常和日志处理方式
当前团队不建议继续沿用的历史写法
AI 绝对不能生成的反例模式
```

### 3. 建设 AI 可执行的 Coding Rules

每个端都要形成专门给 AI 使用的规则文件。

例如：

```text
app-ai-rules.md
frontend-ai-rules.md
backend-ai-rules.md
pc-ai-rules.md
```

AI Rules 要重点回答：

```text
AI 生成代码前必须检查什么
AI 生成代码时必须遵守什么
AI 不能生成哪些代码
AI 修改代码后必须如何自检
```

### 4. 统一各端开发规范

覆盖部门主要研发方向：

```text
APP：Android、iOS、KMP、数据中台、多展业地
PC：Mac、Windows、跨平台公共层、平台适配层
前端：H5、Admin、组件、API、状态、权限、类型
后端：Java、Python、分层、DTO、事务、异常、日志、测试
```

每个端形成：

```text
人读版开发规范
AI 执行版规则
模块级规范模板
正例代码
反例代码
Review Checklist
```

### 5. 建立 AI 辅助研发标准输入

统一 AI 开发上下文包：

```text
需求说明
当前端类型
当前业务模块
相关代码路径
接口文档
设计稿 / 交互说明
全局规范
端规范
模块规范
AI Rules
正例代码
禁止事项
自检清单
```

让 AI 在开始编码前，先理解：

```text
需求属于哪个模块
哪些能力可以复用
哪些逻辑应该放共享层
哪些逻辑应该放平台层
哪些地方不能改
哪些规则必须遵守
```

### 6. 形成统一 Code Review 标准

通过 Review Checklist 统一各端评审标准。

让 reviewer 可以基于规则检查：

```text
是否破坏分层
是否重复实现
是否绕过公共能力
是否直接使用 DTO
是否缺少异常兜底
是否缺少日志和埋点
是否硬编码展业地逻辑
是否缺少必要测试
```

最终做到：

> **规范可引用，问题可定位，Review 可标准化。**

### 7. 建立持续迭代机制

第一版规范不是终点，而是起点。

后续每次出现：

```text
AI 生成错误代码
Code Review 发现高频问题
线上问题暴露规范缺口
新技术栈或新模块引入
多展业地适配出现新模式
```

都要反向沉淀到规范仓库中，持续更新 AI Rules、正反例和 Checklist。

## 五、第一版成功标准

第一版成功不看文档写了多少页，而看是否能真实提升 AI 辅助研发质量。

建议用以下标准衡量：

```text
1. AI 能判断代码应该放在哪个目录、模块和分层。
2. AI 能遵守 APP / 前端 / 后端 / PC 的基本架构规则。
3. AI 能优先复用已有模块、组件、Repository、UseCase。
4. AI 不再随意绕过公共网络、缓存、日志、配置体系。
5. AI 不再把 DTO 直接传递到 UI 层。
6. AI 不再在 UI 层、Controller 层写复杂业务逻辑。
7. AI 能输出修改文件列表、实现方案和自检清单。
8. Code Review 可以直接引用规范指出问题。
9. 新人可以通过规范快速理解团队推荐写法。
10. 团队可以持续把 AI 出错案例沉淀为新规则。
```

## 六、一句话总结

本项目的背景是：

> **AI 辅助研发正在进入真实需求开发阶段，但团队缺少统一、结构化、AI 可执行的研发规范，导致 AI 生成代码容易不符合团队架构和质量要求。**

本项目的目标是：

> **建设部门级 `engineering-standards` 规范仓库，沉淀各端开发规范、AI Coding Rules、正反例、Prompt 模板和 Review Checklist，让 AI 能够按照团队既有架构、工程习惯和质量标准高质量完成需求开发。**
