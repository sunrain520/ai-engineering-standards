
`project-standard-extractor` 不应该默认“一次性抽所有端规范”，而应该设计成：

> **按端、按项目、按代码路径独立运行的规范抽取 Skill。**
> 每次只针对一个端或一个技术域抽取规范，例如 APP、PC、Frontend、Backend、Python、Java、iOS、Android。
> 最终再由 `merge-coordinator` 把不同端的产物合并到 `engineering-standards` 对应目录。

---

# 1. 正确定位

之前方案里“支持多端”容易被理解成：

```text
一次运行
  -> 扫所有项目
  -> 同时输出 APP / PC / Frontend / Backend / Testing / Security 全部规范
```

这不对。

正确方式应该是：

```text
一次运行
  -> 输入某一端的代码路径
  -> 识别该端技术栈
  -> 只抽取该端开发规范
  -> 输出到对应端目录
```

例如：

```text
运行 1：
  输入 Android / KMP 项目
  输出 APP 客户端规范

运行 2：
  输入 H5 / Admin 项目
  输出前端规范

运行 3：
  输入 Java 后端项目
  输出 Java 后端规范

运行 4：
  输入 Python 项目
  输出 Python 后端 / 工具服务规范
```

# 2. Skill 入口应该改成“端域限定”

## 2.1 输入模型

建议把输入从：

```yaml
project_paths:
  - /path/to/project
```

升级为：

```yaml
extraction_target:
  domain: backend
  sub_domain: java

project_paths:
  - /path/to/java-service-a
  - /path/to/java-service-b

output_mode: append-only
```

完整示例：

```yaml
extraction_target:
  domain: app-client
  sub_domain: android-kmp

project_paths:
  - /repos/app-trade
  - /repos/app-market

scope:
  include:
    - shared/
    - androidApp/
    - feature/
    - data/
    - domain/
  exclude:
    - build/
    - generated/
    - .gradle/

output:
  base_dir: engineering-standards/01-app-client
  mode: append-only
```

# 4. 重新设计后的运行模式

## 4.1 单端单项目

适合快速验证。

```text
一个项目
  -> 一个端
  -> 一份规范候选
```

示例：

```text
hszq-app
  -> app-client / android-kmp
  -> standard-android-kmp.md
```

---

## 4.2 单端多项目

这是最推荐的模式。

```text
多个同端优秀项目
  -> 一个端
  -> 抽取团队通用规范
```

示例：

```text
trade-service
account-service
risk-service
  -> backend / java-spring
  -> standard-java-spring.md
```

这种模式最适合抽取“团队规范”，因为它可以判断：

```text
这个模式是不是多个项目都在用？
是不是某个项目的局部习惯？
有没有反例？
是否适合升级为团队级规范？
```

---

## 4.3 多端多次运行

最终部门规范不是一次跑出来的，而是多次独立运行后合并。

```text
Run 1: app-client / android-kmp
Run 2: app-client / ios-reactorkit
Run 3: frontend / h5-admin
Run 4: backend / java-spring
Run 5: backend / python
Run 6: pc-client / windows
Run 7: pc-client / macos
```

最终合并成：

```text
engineering-standards/
  01-app-client/
  02-pc-client/
  03-frontend/
  04-backend/
  05-testing/
  06-release/
  07-security/
  08-ai-coding/
  09-industry/
```

# 5. Skill 工作流要调整

原来的 full-auto 应该改成：

```text
domain-scoped full-auto
```

也就是：

```text
输入指定端
  ↓
只加载该端 profiler
  ↓
只运行该端 collectors
  ↓
只生成该端 pattern candidates
  ↓
只输出该端 standard / ai-rules / checklist
```

## 新流程

```text
1. intake-and-scope
   校验 extraction_target

2. domain-router
   根据 domain/sub_domain 选择端侧 workflow

3. repo-profiler
   只识别当前端相关结构

4. batch-planner
   按当前端拆 batch

5. fact-collector
   只运行当前端 collectors

6. pattern-miner
   只挖当前端开发模式

7. rule-synthesizer
   只生成当前端规范

8. quality-gate
   当前端规则准入

9. merge-coordinator
   append-only 合并到对应端目录
```

# 8. 输出不能互相污染

APP 抽取不能写后端规范。
前端抽取不能写 APP 规范。
Java 抽取不能写 Python 规范。

因此每次运行必须有硬边界：

```text
当前运行：
  domain = backend
  sub_domain = java-spring

允许输出：
  engineering-standards/04-backend/standard-java-spring.md
  engineering-standards/04-backend/ai-rules-java.md
  engineering-standards/04-backend/review-checklist-java.md
  engineering-standards/04-backend/evidence/java/

禁止输出：
  engineering-standards/01-app-client/
  engineering-standards/03-frontend/
  engineering-standards/02-pc-client/
```

# 10. 修改后的 Skill 触发语义

`SKILL.md` 应该明确：

```text
默认不做跨端全量抽取。
每次运行必须绑定一个 extraction_target。
如果用户没有指定端，则根据 project_paths 自动识别，并只选择置信度最高的一个端。
如果识别到多个端，必须拆成多个 run。
```

例如一个 monorepo：

```text
repo/
  apps/admin
  apps/h5
  services/trade
  shared/mobile
```

不能一次混合抽取。应该拆成：

```text
Run 1:
  domain = frontend
  paths = apps/admin, apps/h5

Run 2:
  domain = backend
  paths = services/trade

Run 3:
  domain = app-client
  paths = shared/mobile
```

# 11. 最佳运行策略

## 第一步：按端选黄金样本

```text
APP Android/KMP：
  选 3-5 个优秀 APP 工程

iOS ReactorKit：
  选 3-5 个优秀 iOS 工程

Frontend H5/Admin：
  选 5-10 个优秀前端工程

Java Backend：
  选 10-20 个优秀后端服务

Python：
  选 3-5 个优秀 Python 工具或服务

PC：
  选 3-5 个优秀 PC 工程
```

---

## 第二步：每端独立抽取

```text
backend/java-spring run
frontend/h5-admin run
app-client/android-kmp run
app-client/ios-reactorkit run
backend/python run
pc-client/windows run
pc-client/macos run
```

---

## 第三步：端内合并

例如 Java 后端：

```text
trade-service facts
account-service facts
risk-service facts
  ↓
backend/java-spring pattern candidates
  ↓
standard-java-spring.md
```

---

## 第四步：跨端只做“公共规范提炼”

跨端不是一开始一起抽，而是在各端完成后，再提炼共性。

例如：

```text
APP 规范
Frontend 规范
Backend 规范
PC 规范
  ↓
common pattern mining
  ↓
00-global/
  standard-common.md
  ai-coding-common.md
```

跨端公共规范只适合提炼：

```text
命名原则
日志红线
异常原则
配置原则
敏感信息红线
AI Coding 输出格式
Review 流程
```

不应该把 Java 的分层规范强加给前端，也不应该把前端组件规范强加给 APP。

# 13. 最终设计原则修正

应该明确写进技术方案：

```text
原则 1：
project-standard-extractor 是 domain-scoped extractor，不是 all-in-one generator。

原则 2：
每次运行只处理一个 domain/sub_domain。

原则 3：
多端规范通过多次运行生成，不在一次运行中混合生成。

原则 4：
跨端共性规范只能从已确认的端内规范中二次提炼。

原则 5：
端内规则不能污染其他端目录。

原则 6：
domain-router 决定 collectors、miners、templates、output_dir。

原则 7：
如果输入路径包含多个端，必须拆分为多个 run。
```

---

# 14. 一句话总结

你这个修正是对的。

`project-standard-extractor` 最佳形态应该是：

> **按端运行、端内抽取、端内合并、跨端二次提炼。**

也就是：

```text
不同端的代码
  ↓
分别运行不同 domain extractor
  ↓
分别生成各端开发规范
  ↓
再由 merge / global extractor 提炼公共规范
```

这样才能避免“一次性大而全总结”导致的规范空泛、端侧混淆、证据不清和 AI 执行困难。
