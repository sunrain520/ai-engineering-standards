# 第一阶段技术方案

## 文档状态

本文档是 `engineering-standards` 第一阶段建设的完整技术方案。

> 路径迁移说明：`project-standard-extractor` 的当前 canonical source package 已迁移到 `skills/project-standard-extractor/`。本文正文中出现的 `engineering-standards/08-ai-coding/project-standard-extractor/` 是迁移前的历史路径。

第一阶段最终形态不是规范管理平台，也不是 AI IDE 插件，而是：

> **建设一个可复用的“规范萃取 Skill”，由 Skill 基于团队真实项目代码和研发上下文，输出对应的规范文档内容。**

第一阶段交付重点是：

```text
project-standard-extractor 单一对外 Skill 工作流
    +
规范文档输出模板
    +
APP / 前端 / 后端 / 行业规范首批草稿
    +
AI Coding Rules
    +
Code Review Checklist
    +
多 agent 分面评审、质量门禁和人工确认流程
```

`llms.txt`、`rules-index.json`、多工具规则导出、CI 检查和规范平台属于后续增强能力，第一阶段只保留设计兼容，不作为必须完成的主交付。

## 一、第一阶段定位

### 1. 核心定位

第一阶段的核心定位是：

> **从团队优秀实践中萃取 AI 可执行的研发规范，并输出人能读、AI 能执行、Review 能检查的规范文档。**

它不是“写一批静态规范文档”，而是建立一套稳定方法：

```text
真实项目代码
    ↓
规范萃取 Skill
    ↓
代码事实
    ↓
推荐 / 禁止 / 历史兼容模式
    ↓
规则生成
    ↓
规范文档内容
    ↓
AI Rules / Review Checklist / Prompt 模板
```

### 2. 第一阶段要解决的问题

第一阶段优先解决三个问题：

```text
1. 如何从真实代码中萃取团队规范，而不是凭空写通用规范。
2. 如何把萃取结果输出成团队可直接使用的规范文档。
3. 如何让规范同时服务研发人员、AI 工具和 Code Review。
```

对应到 AI 辅助研发场景，第一阶段要让 AI 至少做到：

```text
知道当前需求属于哪个研发域和业务模块
知道代码应该放在哪个目录、模块和分层
知道哪些逻辑应该复用，哪些逻辑不能重复实现
知道哪些写法是团队禁止的
知道生成代码后如何按规范自检
```

### 3. 第一阶段不做什么

第一阶段明确不做：

```text
1. 不建设规范管理 Web 平台。
2. 不建设复杂 CLI 产品。
3. 不做全量历史代码整改。
4. 不做全自动规范生成并直接合入。
5. 不做大规模向量库检索。
6. 不做多 AI 工具规则自动导出。
7. 不把所有规范规则都自动化扫描。
8. 不一次性覆盖所有研发方向的完整细节。
```

第一阶段要做到：

> **Skill 工作流清楚、输入输出清楚、模板清楚、质量门禁清楚、APP 端样板可用。**

## 二、第一阶段目标

### 1. 业务目标

通过第一阶段建设，让部门拥有一套可复用的规范萃取方法和首批规范文档资产。

目标是让团队从：

```text
靠资深同学口头传递规范
```

升级为：

```text
通过 Skill 从真实代码萃取规范，并输出可复用规范文档
```

### 2. 工程目标

第一阶段需要交付：

```text
1. 规范萃取 Skill 技术方案。
2. 规范萃取输入标准。
3. 规范萃取处理流程。
4. 规范文档输出模板。
5. AI Rules 输出模板。
6. Code Review Checklist 输出模板。
7. 正例 / 反例 / 历史兼容说明模板。
8. APP / 前端 / 后端 / 行业规范结果样板。
9. 多 agent 分面评审、质量门禁和人工确认流程。
10. 第一阶段验收标准。
```

### 3. 成功标准

第一阶段成功不看文档数量，而看是否形成可复用闭环。

成功标准：

```text
1. 能拿一个真实项目作为输入，按流程萃取代码事实。
2. 能区分推荐模式、禁止模式、历史兼容模式和待确认模式。
3. 能输出人读版开发规范。
4. 能输出 AI Coding Rules。
5. 能输出 Code Review Checklist。
6. 每条核心规则有适用范围、Rule ID、AI 要求和 Review 检查项。
7. APP / 前端 / 后端 / 行业规范草稿可被 AI 临时使用，其中 APP 作为复杂端样板验证。
8. Review 可以引用规范条目指出问题。
9. 输出结果不会把历史包袱误写成推荐标准。
10. APP / 前端 / 后端 / 行业规范都能复用同一个对外 Skill 流程。
```

### 2. 第一阶段核心链路

```text
输入项目代码和上下文
    ↓
Skill 先输出代码事实，不直接下结论
    ↓
Skill 将事实分类为推荐 / 禁止 / 历史兼容 / 待确认
    ↓
Skill 生成规则候选
    ↓
Skill 填充规范文档模板
    ↓
Skill 输出 AI Rules 和 Review Checklist
    ↓
Skill 写入正式规范目录并标记 draft
    ↓
端负责人评审后升级 active
```

### 3. 技术选型原则

第一阶段技术选型坚持轻量：

```text
Markdown 作为规范文档主格式
Prompt / Skill 工作流作为规范萃取核心
人工评审作为质量确认环节
Rule ID 作为规则引用基础
JSON / llms.txt 作为后续 AI 索引预留能力
```

不引入：

```text
数据库
向量库
Web 后台
复杂规则引擎
自动合并正式规范的机器人
```

## 五、Skill 设计

### 1. 对外 Skill 数量

```text
project-standard-extractor
```

第一阶段只保留这一个对外 Skill。APP、前端、后端、行业规范、AI Rules、Review Checklist、evidence 和质量评审都由它内部编排完成，不拆成多个对外入口。

这样用户只需要提供一次项目上下文，Skill 内部保证证据口径、规则状态和输出结构一致。

中文名：

```text
项目研发规范萃取 Skill
```

### 2. Skill 定位

Skill 的定位是：

> **输入一个真实项目和研发域，分析代码事实，识别推荐模式、禁止模式和历史兼容模式，输出对应规范文档内容。**

Skill 不是简单总结代码，也不是直接生成理想化规范。

它必须完成：

```text
代码事实提取
→ 推荐模式识别
→ 禁止模式识别
→ 历史兼容识别
→ 规则候选生成
→ 规范文档生成
→ AI Rules 生成
→ Review Checklist 生成
→ 多 agent 分面评审
→ 写入正式规范目录，状态为 draft
```

### 3. Skill 输入

第一阶段 Skill 输入以“人工提供 + AI 辅助分析”为主，不要求实现完整 CLI。

Skill 采用交互式引导输入，不要求用户一次性填写完整表单。推荐引导顺序：

```text
1. project_paths           一个或多个真实项目代码路径
2. dev_domain              研发域
3. industry_domain         行业场景
4. target_scope            输出范围
5. sub_domains             技术栈 / 子领域
6. business_modules        业务模块
7. positive_candidates     正例候选代码路径
8. negative_candidates     反例候选代码路径
9. legacy_candidates       历史兼容候选代码路径
10. existing_docs          已有规范、架构文档、Review 记录
11. quality_focus          本次萃取重点
12. output_target          写入目标目录
13. confirmation           用户确认启动萃取
```

`dev_domain` 推荐枚举：

```text
app-client
pc-client
frontend
backend
testing
release
security
ai-coding
```

`sub_domain` 推荐枚举：

```text
kmp
android
ios
data-center
multi-market
mac
windows
h5
admin
component
api
java
python
database
cache
mq-task
```

### 4. Skill 输出

Skill 直接写入正式规范目录，初始状态为 `draft`。写入时不得覆盖已有 `active`，默认也不得覆盖已有 `draft`；新规则追加为 `draft`，相近规则进入 merge suggestions，冲突规则进入 pending conflict。

建议输出：

```text
{domain-output-dir}/
├── overview.md
├── standard.md
├── ai-rules.md
├── review-checklist.md
├── examples/
├── evidence/
│   ├── code-facts.md
│   ├── positive-examples.md
│   ├── forbidden-examples.md
│   └── legacy-compatible.md
├── pending-confirmation.md
├── merge-suggestions.md
└── conflicts.md
```

核心产物说明：

| 文件 / 目录 | 说明 |
| --- | --- |
| `overview.md` | 研发域概览、适用范围、架构目标 |
| `standard.md` | 人读版规范，规则状态初始为 `draft` |
| `ai-rules.md` | AI 执行版规则，标注高风险 draft 提示 |
| `review-checklist.md` | Review 检查清单，引用 Rule ID |
| `examples/` | 正例、反例、历史兼容示例说明 |
| `evidence/` | 独立证据目录，保存代码事实和真实路径证据 |
| `pending-confirmation.md` | 证据不足或有争议，需要人工确认 |
| `merge-suggestions.md` | 与已有规则语义相近的合并建议 |
| `conflicts.md` | 与已有 active / draft 冲突的待确认项 |

### 5. 内部 agent 拆分

`project-standard-extractor` 对外只有一个入口，内部采用混合 agent 模型：

| 类型 | Agent | 职责 |
| --- | --- | --- |
| 通用阶段 | Intake | 交互式引导输入，确认萃取边界和输出目标 |
| 通用阶段 | Project Profiler | 识别项目类型、技术栈、模块边界、目录结构 |
| 通用阶段 | Evidence Collector | 收集代码路径、正例、反例、历史兼容证据 |
| 通用阶段 | Code Facts | 输出代码事实，不直接生成规范结论 |
| 通用阶段 | Pattern Classifier | 将事实分类为推荐、禁止、历史兼容、待确认 |
| 专项生成 | APP / Frontend / Backend Standard | 生成对应端的规范草稿 |
| 专项生成 | Industry Standard | 生成独立行业规范草稿 |
| 专项生成 | AI Rules | 将规则压缩成 AI 可执行指令 |
| 专项生成 | Review Checklist | 将规则转成可检查清单 |
| 证据输出 | Evidence Writer | 写入独立 evidence，不把代码路径塞进规则正文 |
| 分面评审 | Evidence Auditor | 检查规则是否有真实证据支撑 |
| 分面评审 | Team Standard Reviewer | 检查规则是否是团队级标准，而不是项目说明书 |
| 分面评审 | AI Executability Reviewer | 检查规则是否能被 AI 执行和自检 |
| 分面评审 | Review Checklist Reviewer | 检查规则是否能被人工 Review 判断 |
| 分面评审 | Conflict Reviewer | 检查与已有 active / draft 规则是否重复或冲突 |
| 分面评审 | Industry Risk Reviewer | 检查行业规则是否过度推断、是否需待确认 |
| 汇总写入 | Quality Gate | 汇总分面评审结果，给出状态建议 |
| 汇总写入 | Merge Coordinator | 追加 draft、证据、合并建议和冲突待确认 |

执行顺序遵循：

```text
Intake / Project Profiler
    ↓
Evidence Collector / Code Facts / Pattern Classifier
    ↓
APP / Frontend / Backend / Industry / AI Rules / Review Checklist 并行生成
    ↓
Evidence Auditor / Team Standard Reviewer / AI Executability Reviewer / Checklist Reviewer / Conflict Reviewer / Industry Risk Reviewer 并行评审
    ↓
Quality Gate 汇总
    ↓
Merge Coordinator 写入正式规范目录
```

## 六、Skill 工作流

### 1. Step 0：任务受理

目标是确认本次萃取范围。

必须明确：

```text
项目路径
研发域
技术栈
业务模块
输出目标
是否有候选正例
是否有候选反例
是否只做草稿
```

输出：

```text
analysis-scope.md
```

### 2. Step 1：项目画像

分析项目的基础信息：

```text
项目类型
技术栈
构建工具
测试框架
主要目录
核心模块
代码量级
可能的架构模式
```

输出：

```text
analysis-report.md
```

### 3. Step 2：样本选择

不全量读取所有代码，优先选择高价值样本。

优先样本：

```text
文件结构完整的模块
调用链清晰的业务闭环
最近仍在维护的代码
团队公认质量较高的代码
有测试覆盖的代码
能体现核心架构模式的代码
被多个地方复用的代码
```

输出：

```text
sample-selection.md
```

### 4. Step 3：代码事实提取

这一阶段只输出事实，不生成规范。

事实维度：

```text
目录结构事实
文件命名事实
类 / 函数 / 变量命名事实
分层架构事实
模块职责事实
数据流转事实
API 调用事实
状态管理事实
异常处理事实
日志 / 埋点事实
配置管理事实
测试事实
复用模式事实
不一致写法事实
疑似坏味道事实
```

每个事实必须带证据路径。

输出：

```text
code-facts.md
```

### 5. Step 4：模式分类

将代码事实分类为四类：

| 类型 | 定义 | 处理方式 |
| --- | --- | --- |
| 推荐模式 | 符合团队目标、质量较高、适合 AI 模仿 | 写入规范 |
| 禁止模式 | 明确不希望 AI 继续生成 | 写入禁止规则和反例 |
| 历史兼容模式 | 历史代码存在，但不推荐新增 | 写入历史兼容说明 |
| 待人工确认模式 | 证据不足或团队可能有争议 | 不进入正式 P0，等待确认 |

输出：

```text
recommended-patterns.md
forbidden-patterns.md
legacy-patterns.md
pending-confirmation.md
```

### 6. Step 5：规则生成

基于推荐模式和禁止模式生成规则候选。

每条规则必须包含：

```text
Rule ID
规则标题
规则级别
适用范围
规则说明
推荐写法
禁止写法
AI 生成代码要求
Code Review 检查项
证据索引
置信度
风险级别
```

规则等级：

| 等级 | 含义 | 处理方式 |
| --- | --- | --- |
| P0 | 强制规则 | AI 必须遵守，Review 必须检查 |
| P1 | 推荐规则 | 新代码默认遵守 |
| P2 | 建议规则 | 可作为优化方向 |
| LEGACY | 历史兼容 | 解释历史代码，不推荐新增 |
| FORBIDDEN | 禁止规则 | AI 不得生成，新代码不得新增 |

输出：

```text
rules.candidate.md
```

### 7. Step 6：规范文档生成

将规则候选填充到文档模板中，输出三类文档：

```text
人读版开发规范
AI 执行版规则
Review 检查版清单
```

输出：

```text
standard.md
ai-rules.md
review-checklist.md
```

### 8. Step 7：质量门禁

Skill 输出结果必须先经过内部多 agent 分面评审，再由 Quality Gate 汇总。

质量门禁包括：

```text
证据门禁
团队级抽象门禁
AI 可执行门禁
Review 可检查门禁
冲突门禁
行业风险门禁
正反例门禁
规则数量门禁
```

未通过门禁的规则不得进入 `draft` 正文，只能进入 `pending-confirmation.md`、`conflicts.md` 或 `legacy-compatible`。

### 9. Step 8：人工评审与状态流转

Skill 写入 `draft` 后，必须由对应端负责人审核确认，才能升级为 `active`。架构负责人、行业 / 合规 / 安全负责人可参与高风险规则评审，但不是所有规则的必经审批人。

状态流转：

```text
Skill 写入 draft
    ↓
端负责人 Review
    ↓
高风险规则按需升级多人确认
    ↓
修改规则级别、措辞和适用范围
    ↓
通过项 draft -> active
    ↓
未通过项保留 pending / conflict / legacy-compatible / rejected
```

### 10. Step 9：真实需求试点

文档发布前，必须用真实需求验证。

建议每个端选择：

```text
2 到 3 个真实需求
1 个常规需求
1 个复杂状态 / 数据流需求
1 个历史易错场景
```

验证问题：

```text
AI 是否放对目录
AI 是否遵守分层
AI 是否复用已有能力
AI 是否绕过公共能力
AI 是否直接使用 DTO / Entity
AI 是否生成重复逻辑
AI 是否输出自检清单
Reviewer 是否能引用规则指出问题
```

## 八、Rule ID 设计

### 1. Rule ID 格式

```text
STD-{DOMAIN}-{SUB_DOMAIN}-{LEVEL}-{NUMBER}
```

示例：

```text
STD-APP-KMP-P0-001
STD-APP-ANDROID-P0-001
STD-APP-IOS-P0-001
STD-BE-JAVA-P0-001
STD-FE-ADMIN-P0-001
```

### 2. DOMAIN 缩写

| 研发领域 | 缩写 |
| --- | --- |
| Global | GL |
| App Client | APP |
| PC Client | PC |
| Frontend | FE |
| Backend | BE |
| Testing | TEST |
| Release | REL |
| Security | SEC |
| AI Coding | AI |

### 3. LEVEL 定义

| 级别 | 含义 | AI 行为 |
| --- | --- | --- |
| P0 | 强制规则 | 必须遵守 |
| P1 | 推荐规则 | 默认遵守 |
| P2 | 建议规则 | 尽量遵守 |
| LEGACY | 历史兼容 | 只解释历史代码，不推荐新增 |
| FORBIDDEN | 禁止规则 | 不得生成，不得新增 |

### 4. 锚点要求

每条核心规则前增加固定锚点：

```markdown
<a id="STD-APP-ANDROID-P0-001"></a>

## STD-APP-ANDROID-P0-001：Activity / Fragment 不得直接请求网络
```

这样 AI、Review 和后续索引都能稳定引用。

## 九、质量门禁设计

### 1. 证据门禁

每条核心规则必须能回答：

```text
这条规则来自哪个项目？
来自哪些代码路径？
是否有正例？
是否有反例？
是否是团队真实推荐写法？
是否只是历史包袱？
```

门禁要求：

```text
P0 规则：必须有明确代码证据或真实 Review / 线上问题证据。
P1 规则：至少有代码、文档或团队约定证据。
P2 规则：可以来自架构建议，但必须标记为建议。
无证据规则：不得进入正式规范，只能进入待确认。
```

### 2. AI 可执行门禁

每条规则必须回答：

```text
AI 生成代码前必须检查什么？
AI 生成代码时必须遵守什么？
AI 不得生成什么？
AI 生成后必须如何自检？
```

不能指导 AI 写代码的内容，不进入 AI Rules。

### 3. Review 可检查门禁

每条 P0 规则必须有可判断的 Review 检查项。

不合格写法：

```text
代码要清晰。
模块要解耦。
异常要合理处理。
```

合格写法：

```text
Controller 不得直接访问 Mapper。
UI 层不得直接请求网络。
DTO 不得直接进入 UI 层。
```

### 4. 正反例门禁

核心主题至少要有：

```text
1 个正例
1 个反例
1 个正确改法或说明
```

### 5. 数量门禁

第一阶段不要追求完整百科。

每个端建议：

```text
P0 强制规则：10 条左右
P1 推荐规则：10 到 20 条
FORBIDDEN 禁止规则：5 到 10 条
LEGACY 历史兼容：按需补充
```

### 6. 规则质量评分卡

每条规则合入前可以按 10 分制评估：

| 维度 | 分值 | 判断标准 |
| --- | ---: | --- |
| 证据充分性 | 2 | 是否来自真实代码 / 真实问题 |
| 表达清晰度 | 2 | 是否具体、无歧义 |
| AI 可执行性 | 2 | AI 是否知道怎么做 |
| Review 可检查性 | 2 | Reviewer 是否能判断是否违反 |
| 正反例完整性 | 1 | 是否有正例 / 反例 |
| 适用边界清晰度 | 1 | 是否说明适用范围 |

低于 7 分不进入正式规范。

### Prompt 1：项目画像

```markdown
你是资深研发架构师。

请基于项目文件索引、关键配置和候选代码路径，识别项目类型、技术栈、主要模块、目录结构和潜在架构模式。

不要生成规范，只输出项目画像。

输出：
1. 项目类型
2. 技术栈
3. 主要模块
4. 主要目录
5. 架构模式推断
6. 需要重点分析的文件
7. 不确定事项
```

### Prompt 2：代码事实提取

```markdown
你是代码规范萃取专家。

请基于给定代码片段和文件路径提取代码事实，不要直接生成规范。

每个事实必须带文件路径证据。

必须输出：
1. 目录结构事实
2. 命名事实
3. 分层事实
4. 数据流事实
5. 状态管理事实
6. 异常处理事实
7. 日志 / 埋点事实
8. 测试事实
9. 复用模式
10. 不一致点
11. 疑似坏味道
```

### Prompt 3：模式分类

```markdown
你是研发规范治理专家。

请将代码事实分类为：

1. 推荐模式
2. 禁止模式
3. 历史兼容模式
4. 待人工确认模式

分类时必须说明理由和证据。

禁止把历史代码中存在的写法直接视为推荐规范。
```

### Prompt 4：规则生成

```markdown
你是部门级研发规范专家。

请基于推荐模式和禁止模式生成规范规则。

每条规则必须包含：

2. 规则标题
3. 规则级别
4. 适用范围
5. 规则说明
6. 推荐写法
7. 禁止写法
8. AI 生成代码要求
9. Code Review 检查项
10. 证据索引
11. 置信度
12. 风险级别

只生成有证据支撑的规则。
```

### Prompt 5：规范文档生成

```markdown
你是技术规范文档专家。

请将已确认的规则填充到指定开发端规范模板中。

要求：
1. 保留模板结构。
2. 优先填充有证据支撑的内容。
3. 对证据不足的部分标记“待人工确认”。
4. 不编造项目不存在的技术栈。
5. 输出适合团队评审的规范草稿。
```

### Prompt 6：AI Rules 生成

```markdown
你是 AI Coding Rules 专家。

请将人读版规范压缩为 AI 可执行规则。

要求：
1. 使用命令式表达。
2. 使用“必须 / 不得 / 禁止 / 生成前先检查”。
3. 不写模糊建议。
4. 控制长度。
5. 优先保留 P0 和 FORBIDDEN 规则。
```

### Prompt 7：Review Checklist 生成

```markdown

2. 每个检查项尽量可判断。
3. P0 规则必须有检查项。
4. 检查项可以引用 Rule ID。
```

## 十二、评审与状态流转流程

### 1. 状态流转流程

```text
Skill 写入 draft
    ↓
端负责人检查技术真实性
    ↓
高风险规则按需升级架构 / 行业 / 安全负责人确认
    ↓
AI 使用者检查可执行性
    ↓
补充证据和正反例
    ↓
调整规则等级
    ↓
通过项 draft -> active
    ↓
记录 CHANGELOG
```

### 2. 评审角色

| 角色 | 评审重点 |
| --- | --- |
| 端负责人 | 是否符合当前端真实架构，是否把历史包袱写成推荐规范 |
| 资深研发 | 是否能指导日常开发，正反例是否真实 |
| 架构负责人 | 只对高风险架构边界规则按需参与确认 |
| 行业 / 安全 / 合规负责人 | 只对行业高风险、安全、合规、资金链路规则按需确认 |
| AI 使用者 | AI 是否能理解，AI Rules 是否足够短硬 |
| Reviewer | Checklist 是否可执行，问题是否可定位 |

### 3. 合入原则

```text
1. Skill 可直接写入正式规范目录，但初始状态只能是 draft。
2. 无证据 P0 / FORBIDDEN 规则不得进入 active。
3. 历史代码存在的写法不默认视为推荐规范。
4. 争议规则进入待确认，不进入强制规则。
5. P0 规则必须有 AI 生成要求和 Review 检查项。
6. 规则变更必须记录变更原因。
7. 重复运行不得覆盖已有 active，默认也不得覆盖已有 draft。
```

```text
examples 目录有正反例说明。
evidence 目录有真实代码路径证据。
```

### Milestone 4：试点验证

目标：

```text
选择 1 到 2 个真实需求，用 APP / 前端 / 后端规范和 Prompt 驱动 AI 输出方案或代码。
记录 AI 是否能遵守规范。
记录 Review 问题。
反向修订规范。
```

验收：

```text
AI 能输出需求归属判断。
AI 能引用规范自检。
Review 可以引用规范指出问题。
至少沉淀 1 轮规则修订。
```

## 十六、风险与应对

| 风险 | 表现 | 应对 |
| --- | --- | --- |
| 规范写成通用原则 | AI 无法执行，Review 无法检查 | 每条 P0 必须有 AI 要求和 Review 检查项 |
| 把历史包袱写成标准 | AI 复制错误模式 | 强制区分推荐 / 禁止 / 历史兼容 |
| 文档过长 | AI 抓不住重点，研发不愿看 | 人读版和 AI Rules 分离 |
| 证据不足 | 规范不符合真实项目 | 无证据规则进入待确认 |
| 过早平台化 | 成本高，主线发散 | 第一阶段只做 Skill 和文档输出 |
| 缺少试点 | 文档看起来完整但不能用 | 每个端至少用真实需求验证 |

## 十七、第一阶段验收标准

### 1. 方案验收

```text
第一阶段技术方案完成。

方案明确 Skill 输出规范文档内容。
方案明确第一阶段做什么和不做什么。
```

```text
Skill 输入标准清楚。
```

### 4. 内容质量验收

```text
规范不是凭空编写。
```

## 十八、最终结论

第一阶段最终交付的不是一个完整平台，而是一套可复用的规范萃取闭环：

```text
真实项目代码和团队上下文
    ↓
规范萃取 Skill
    ↓
代码事实和模式分类
    ↓
规范规则
    ↓
人读版规范
    ↓
AI Coding Rules
    ↓
Code Review Checklist
    ↓
真实需求试点
    ↓
规范持续迭代
```

一句话总结：

> **第一阶段要把“怎么从真实代码中萃取团队规范，并输出可被人、AI、Review 使用的规范文档”这件事跑通。**

只有这个闭环跑通之后，再考虑 `llms.txt`、`rules-index.json`、多工具导出、CI 检查和规范平台，才有稳定的内容基础。
