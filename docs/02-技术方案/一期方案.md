# engineering-standards 第一版本轻量化技术方案

## 一、方案定位

第一版本不做完整规范平台，也不做复杂知识库系统。

V1 的核心定位是：

> **建设一套轻量、可维护、可被 AI 消费、可被 Code Review 引用的部门级研发规范工程。**

第一版只解决三个关键问题：

```text
1. 人能快速找到对应端的开发规范
2. AI 能快速加载相关规范
3. 规则能被稳定引用和持续迭代
```

所以 V1 采用最小闭环：

```text
Markdown 文档
+ YAML Front Matter
+ Rule ID
+ rules-index.json
+ llms.txt
```

暂不引入复杂的规则平台、CLI 查询、多索引文件、强 CI 治理和每条规则独立文件。

---

# 二、建设目标

## 1. 业务目标

通过 `engineering-standards` 仓库沉淀部门级研发规范，支撑 AI 辅助研发在真实需求开发中稳定落地。

目标是让 AI 从：

```text
会写代码
```

升级为：

```text
按团队架构、团队规范、团队质量标准写代码
```

---

## 2. 工程目标

第一版本需要交付：

```text
1. 统一 Git 规范仓库
2. 统一目录结构
3. 各端开发规范 Markdown
4. 各端 AI Coding Rules
5. 每条核心规则具备 Rule ID
6. 一个轻量 rules-index.json
7. 一个 AI 入口 llms.txt
8. 一套规范模板
9. 一套人工维护和 Review 流程
```

---

# 三、V1 不做什么

第一版本明确不做以下内容：

```text
1. 不做规范管理平台
2. 不做每条规则一个 Markdown 文件
3. 不做复杂 rule-meta 注释块
4. 不做多个索引文件
5. 不做 CLI 查询工具
6. 不做自动规则推荐系统
7. 不做复杂 CI 校验
8. 不做全量历史代码整改
9. 不做规则与代码一致性自动扫描
10. 不追求一次性覆盖所有细节
```

这些可以放到 V2 / V3。

第一版要做到：

> **简单、能跑、能用、能迭代。**

# 七、目录设计原则

## 1. 一级目录按研发领域划分

不建议一级目录直接按语言拆。

推荐：

```text
app-client
pc-client
frontend
backend
```

原因是你们的规范核心不是语言语法，而是工程领域、架构分层、模块边界和 AI 生成约束。

---

## 2. 二级目录按技术栈细分

例如后端：

```text
04-backend/
├── 01-backend-common-standard.md
├── 02-java/
└── 03-python/
```

含义是：

```text
backend：后端通用规范
java：Java 后端落地规范
python：Python 后端落地规范
```

---

## 3. APP 端按架构能力拆分

APP 端不是简单 Android / iOS 两套规范，而是：

```text
KMP 共享层
Android 平台层
iOS 平台层
数据中台
多展业地配置化
```

所以目录设计为：

```text
01-app-client/
├── 01-kmp/
├── 02-android/
├── 03-ios/
├── 04-data-center/
└── 05-multi-market/
```

# 九、Rule ID 设计

每条核心规则必须有稳定 Rule ID。

## 1. Rule ID 格式

```text
STD-{DOMAIN}-{SUB_DOMAIN}-{LEVEL}-{NUMBER}
```

示例：

```text
STD-GL-COMMON-P0-001
STD-BE-COMMON-P0-001
STD-BE-JAVA-P0-001
STD-BE-PY-P0-001
STD-APP-KMP-P0-001
STD-APP-ANDROID-P0-001
STD-APP-IOS-P0-001
STD-FE-ADMIN-P0-001
STD-FE-H5-P1-001
```

规则 ID 必须包含 `SUB_DOMAIN`。如果规则属于全局或领域通用规范，没有自然技术栈归属，统一使用 `COMMON` 作为子领域，例如 `STD-GL-COMMON-P0-001`、`STD-BE-COMMON-P0-001`。

---

## 2. DOMAIN 缩写

| 研发领域       | 缩写   |
| ---------- | ---- |
| Global     | GL   |
| App Client | APP  |
| PC Client  | PC   |
| Frontend   | FE   |
| Backend    | BE   |
| Testing    | TEST |

---

## 3. SUB_DOMAIN 缩写

| 子领域       | 缩写      |
| --------- | ------- |
| Common    | COMMON  |
| Java      | JAVA    |
| Python    | PY      |
| Android   | ANDROID |
| iOS       | IOS     |
| KMP       | KMP     |
| Data Center | DATA  |
| Multi Market | MARKET |
| H5        | H5      |
| Admin     | ADMIN   |
| Component | COMPONENT |
| API       | API     |
| Database  | DB      |
| Cache     | CACHE   |
| MQ / Task | MQTASK  |

---

## 4. LEVEL 定义

| 级别        | 含义   | AI 行为         |
| --------- | ---- | ------------- |
| P0        | 强制规则 | 必须遵守          |
| P1        | 推荐规则 | 默认遵守          |
| P2        | 建议规则 | 尽量遵守          |
| LEGACY    | 历史兼容 | 只解释历史代码，不推荐新增 |
| FORBIDDEN | 禁止规则 | 不得生成，不得新增     |

# 十、规则块模板

V1 不使用复杂 `rule-meta`，直接使用 Markdown 标题和固定小节。

```markdown
## STD-BE-JAVA-P0-001：Controller 不得写业务逻辑

### 规则说明

Controller 只负责参数接收、参数校验和结果返回，不得承载复杂业务逻辑。

### 推荐写法

- Controller 接收 Request。
- Controller 调用 Service。
- Controller 返回 Response。
- 复杂业务编排放入 Service。
- 核心业务规则放入 Domain Service。

### 禁止写法

- Controller 直接访问 Mapper。
- Controller 直接操作 Entity。
- Controller 中编写复杂业务判断。
- Controller 中编写事务控制逻辑。

### AI 生成代码要求

AI 生成 Java 后端接口时，必须：

1. 将业务逻辑放入 Service。
2. 不得在 Controller 中直接访问 Mapper。
3. 不得直接返回 Entity。
4. 必须定义 Request / Response。
5. 生成代码后必须输出分层自检结果。

### Code Review 检查项

- Controller 是否存在复杂业务逻辑？
- Controller 是否直接访问 Mapper？
- Controller 是否直接返回 Entity？
- Controller 是否只负责请求接收、校验和响应返回？
```

# 十二、Markdown 锚点设计

为了避免不同平台中文标题锚点不一致，建议每条规则前加 HTML anchor。

```markdown
<a id="STD-BE-JAVA-P0-001"></a>

## STD-BE-JAVA-P0-001：Controller 不得写业务逻辑
```

这样索引中的 anchor 固定为：

```text
#STD-BE-JAVA-P0-001
```

AI 和文档系统都能稳定引用。

## 4. build-rules-index.ts 逻辑

伪代码：

```typescript
import fs from "fs";
import path from "path";
import matter from "gray-matter";
import { globSync } from "glob";

const root = path.resolve("../..");

const files = globSync("**/*.md", {
  cwd: root,
  ignore: [
    "node_modules/**",
    ".git/**",
    ".index/**",
    "tools/**"
  ]
});

const rules = [];

for (const file of files) {
  const fullPath = path.join(root, file);
  const content = fs.readFileSync(fullPath, "utf-8");
  const parsed = matter(content);
  const meta = parsed.data;
  const body = parsed.content;

  const ruleRegex = /^##\s+(STD-[A-Z]+-[A-Z0-9]+-(P0|P1|P2|LEGACY|FORBIDDEN)-\d{3})：(.+)$/gm;

  let match;

  while ((match = ruleRegex.exec(body)) !== null) {
    const ruleId = match[1];
    const level = match[2];
    const title = match[3];

    rules.push({
      rule_id: ruleId,
      title,
      domain: meta.domain || "",
      sub_domain: meta.sub_domain || "",
      level,
      source_doc: file,
      anchor: `#${ruleId}`,
      tags: meta.tags || []
    });
  }
}

const output = {
  version: "v1.0.0",
  generated_at: new Date().toISOString(),
  rules
};

fs.mkdirSync(path.join(root, ".index"), { recursive: true });
fs.writeFileSync(
  path.join(root, ".index/rules-index.json"),
  JSON.stringify(output, null, 2),
  "utf-8"
);
```

## 1. APP 端 V1 优先规则

```text
1. 可跨端业务逻辑优先下沉 KMP
2. Android / iOS 不得重复实现核心业务规则
3. UI 层不得直接访问网络

5. 数据访问统一走 Repository / HSDataCenterKit

8. 多展业地差异优先配置化
9. 不得在页面层硬编码展业地逻辑
10. 交易 / 账户 / 订单逻辑必须有异常兜底和日志
```

## 2. 后端 V1 优先规则

```text
1. Controller 不得写业务逻辑
2. Controller 不得直接访问 Mapper / Repository
3. 不得直接返回 Entity
```

# 二十二、最终结论

优化后的第一版本采用轻量方案：

```text
Markdown + Front Matter + Rule ID + rules-index.json + llms.txt
```

这套方案的优势是：

```text
1. 简单，团队容易维护
2. 成本低，第一版能快速落地
3. 对人友好，文档仍然完整可读
4. 对 AI 友好，有统一入口和规则索引
5. 对 Review 友好，问题可以引用 Rule ID
6. 可演进，后续可以自然升级为规范平台
```

一句话总结：

> **V1 不建设复杂规范平台，只建设一套轻量但完整的“人能读、AI 能找、规则能引用、团队能迭代”的研发规范工程。**
