要保障质量，核心不是“多写”，而是建立一套 **规范产出质量门禁**。

你们做的是：

> **从团队优秀实践中沉淀 AI 可执行的研发编码契约。**

所以文档质量应该按下面 6 个标准判断：

```text
1. 是否来自真实代码证据
2. 是否表达为 AI 可执行规则
3. 是否能被研发人员理解
4. 是否能被 Code Review 检查
5. 是否能被工具或流程部分约束
6. 是否经过真实需求试点验证
```

---

# 一、先定义什么是“高质量规范”

高质量规范不是这样的：

```text
代码要清晰。
模块要解耦。
命名要规范。
异常要合理处理。
AI 生成代码要注意质量。
```

这类内容看起来正确，但 AI 很难执行，Review 也很难检查。

高质量规范应该是这样的：

```text
STD-BE-JAVA-P0-001：Controller 不得写业务逻辑

规则说明：
Controller 只负责参数接收、参数校验和结果返回。

推荐写法：
Controller → Service → Repository / Mapper。

禁止写法：
Controller 直接访问 Mapper。
Controller 直接操作 Entity。
Controller 中编写复杂业务判断。

AI 生成代码要求：
AI 新增接口时，必须创建 Request / Response。
业务逻辑必须放入 Service。
不得在 Controller 中直接访问 Mapper。

Code Review 检查项：
Controller 是否存在复杂业务逻辑？
Controller 是否直接访问 Mapper？
Controller 是否直接返回 Entity？
```

也就是说，高质量规范必须做到：

> **有证据、有边界、有正例、有反例、有 AI 要求、有 Review 检查项。**

---

# 二、建立“规范质量六道门禁”

## 1. 证据门禁：每条规则必须来自真实代码或真实问题

第一版规范不能凭空写，也不能照搬行业最佳实践。

每条核心规则都要能回答：

```text
这条规则来自哪个项目？
来自哪些代码路径？
是否有正例？
是否有反例？
是否是团队真实推荐写法？
是否只是历史包袱？
```

建议每条规则后面都保留证据：

```markdown
### 证据来源

正例：
- order-service/src/main/java/.../OrderController.java
- order-service/src/main/java/.../OrderService.java

反例：
- legacy-order/src/main/java/.../LegacyOrderController.java

结论：
当前团队推荐 Controller 只做请求接入，业务逻辑下沉 Service。
```

质量要求：

```text
P0 规则：必须有明确代码证据或线上 / Review 问题证据
P1 规则：至少有一个代码或文档证据
P2 规则：可以来自架构建议，但必须标记为建议
无证据规则：不得进入正式规范，只能进入“待确认”
```

这样可以避免写出“看起来很对，但团队根本没这么做”的文档。

---

## 2. 可执行门禁：每条规则必须能指导 AI 生成代码

每条规范都要经过一个问题拷问：

> **AI 看完这条规则，知道应该怎么写代码吗？**

如果 AI 仍然不知道怎么做，这条规则就是低质量规则。

低质量写法：

```text
Service 层要保持职责清晰。
```

高质量写法：

```text
Service 层负责业务编排，不得直接返回数据库 Entity。
如果接口需要返回数据，必须转换为 Response DTO。
如果已有 Converter，必须复用已有 Converter。
```

建议每条规则都强制包含：

```text
AI 生成代码前必须检查什么
AI 生成代码时必须遵守什么
AI 不得生成什么
AI 生成后必须如何自检
```

例如：

```markdown
### AI 生成代码要求

AI 新增订单查询接口时，必须：

1. 先检查是否已有 OrderService / OrderRepository。
2. 不得新建重复 Service。
3. Controller 只接收 OrderQueryRequest。
4. 查询逻辑放入 OrderService。
5. 返回 OrderQueryResponse。
6. 不得直接返回 OrderEntity。
7. 生成后输出自检结果，并引用本规则 ID。
```

---

## 3. 可检查门禁：每条 P0 规则必须能被 Review 检查

如果一条规则不能被 reviewer 判断，那它就不适合作为强制规则。

例如：

```text
代码要优雅。
```

无法检查。

应该改成：

```text
Controller 方法不得超过 80 行。
Controller 不得直接调用 Mapper。
Controller 不得包含事务注解。
Controller 不得直接返回 Entity。
```

每条 P0 规则必须配：

```markdown
### Code Review 检查项

- 是否存在跨层调用？
- 是否绕过公共能力？
- 是否重复实现已有模块？
- 是否缺少异常处理？
- 是否缺少必要日志？
- 是否直接使用 DTO / Entity？
```

质量要求：

```text
P0 规则没有 Review 检查项，不允许合入。
P0 规则检查项不可判断，不允许合入。
P0 规则只写原则不写检查点，不允许合入。
```

---

## 4. 正反例门禁：每个核心主题必须有正例和反例

AI 很擅长模仿，所以正反例非常重要。

只写规则，AI 可能理解不稳定。
加上正例和反例，AI 才知道团队到底想要什么。

每个核心主题至少要有：

```text
1 个正例
1 个反例
1 个正确改法
```

例如：

````markdown
## 正例：Controller 只调用 Service

```java
@RestController
@RequestMapping("/orders")
public class OrderController {

    private final OrderService orderService;

    @PostMapping("/query")
    public OrderQueryResponse query(@RequestBody OrderQueryRequest request) {
        return orderService.query(request);
    }
}
```

## 反例：Controller 直接访问 Mapper

```java
@RestController
public class OrderController {

    private final OrderMapper orderMapper;

    @PostMapping("/query")
    public List<OrderEntity> query(@RequestBody OrderQueryRequest request) {
        return orderMapper.selectByUserId(request.getUserId());
    }
}
```

````

正反例不一定都要放在主文档里，也可以放在 `examples/` 目录。

但核心 P0 规则最好至少有一个简短示例。

---

## 5. 精简门禁：第一版只保留高价值规则

第一版最容易犯的错误是：

> 什么都想写，最后没人看，AI 也抓不住重点。

建议第一版每个端只保留：

```text
P0 强制规则：10 条左右
P1 推荐规则：10 到 20 条
FORBIDDEN 禁止规则：5 到 10 条
LEGACY 历史兼容：按需补充
```

第一版不追求“完整”，追求“有效”。

进入 V1 的规则必须满足至少一个条件：

```text
1. AI 经常写错
2. 新人经常写错
3. Code Review 经常指出
4. 线上质量风险高
5. 架构破坏成本高
6. 多端一致性要求高
7. 涉及交易、账户、订单、资金等高风险模块
```

不满足这些条件的，先不进第一版。

---

## 6. 试点门禁：必须经过真实需求验证

文档写完不算完成。

必须用真实需求验证：

```text
AI 按这份规范能不能写出更符合团队标准的代码？
Reviewer 能不能直接引用规则指出问题？
新人能不能看懂并照着写？
```

建议每个端选 2 到 3 个真实需求试点：

```text
APP：一个页面需求 + 一个数据请求需求
后端：一个查询接口 + 一个写操作接口
前端：一个列表页 + 一个表单页
```

试点时记录：

```text
AI 是否放对目录
AI 是否遵守分层
AI 是否复用已有能力
AI 是否绕过公共能力
AI 是否直接使用 DTO / Entity
AI 是否生成重复逻辑
AI 是否输出自检清单
Review 问题数量是否下降
```

只有通过试点的规则，才算真正有效。

# 三、建立“规则质量评分卡”

每条规则合入前可以打分。

满分 10 分，低于 7 分不进入正式规范。

| 维度          | 分值 | 判断标准               |
| ----------- | -: | ------------------ |
| 证据充分性       |  2 | 是否来自真实代码 / 真实问题    |
| 表达清晰度       |  2 | 是否具体、无歧义           |
| AI 可执行性     |  2 | AI 是否知道怎么做         |
| Review 可检查性 |  2 | Reviewer 是否能判断是否违反 |
| 正反例完整性      |  1 | 是否有正例 / 反例         |
| 适用边界清晰度     |  1 | 是否说明适用范围           |

示例：

```text
规则：Controller 不得直接访问 Mapper

证据充分性：2
表达清晰度：2
AI 可执行性：2
Review 可检查性：2
正反例完整性：1
适用边界清晰度：1

总分：10
结论：可进入 P0
```

再看一个低质量规则：

```text
规则：代码要保持良好可维护性

证据充分性：0
表达清晰度：0
AI 可执行性：0
Review 可检查性：0
正反例完整性：0
适用边界清晰度：0

总分：0
结论：不得进入规范
```

# 四、输出文档必须经过“三类人”评审

不要只让一个人写完就发布。

至少经过三类角色评审：

## 1. 端负责人评审

负责判断：

```text
是否符合当前端真实架构
是否把历史包袱写成了推荐规范
是否遗漏关键约束
规则级别是否合理
```

## 2. 资深研发评审

负责判断：

```text
规则是否能指导日常开发
正反例是否真实
Review 检查项是否可操作
是否会增加不必要研发负担
```

## 3. AI 使用者评审

负责判断：

```text
AI 能不能理解
Prompt 是否能直接使用
AI Rules 是否太长
AI Rules 是否足够强约束
AI 是否仍然会误解
```

这三类评审都通过，文档质量才比较稳。

# 五、规范文档应该分成三种形态

为了保证落地质量，不要只输出一种长文档。

## 1. 人读版

用于新人、研发、架构师阅读。

```text
java-standard.md
android-standard.md
frontend-standard.md
```

要求：

```text
解释清楚
有背景
有正反例
有适用范围
```

---

## 2. AI 执行版

用于 Cursor、Codex、Claude Code、Copilot。

```text
java-ai-rules.md
android-ai-rules.md
frontend-ai-rules.md
```

要求：

```text
短
硬
明确
命令式
少解释
多禁止
多必须
```

例如：

```text
你必须……
你不得……
生成代码前必须检查……
生成代码后必须自检……
```

---

## 3. Review 检查版

用于 Code Review。

```text
java-review-checklist.md
app-review-checklist.md
frontend-review-checklist.md
```

要求：

```text
可判断
可打勾
可引用 Rule ID
不要写抽象原则
```

# 六、对 Skill 输出增加质量门禁

你们前面设计的 `project-standard-extractor` Skill，必须内置质量控制。

Skill 输出不能直接进入正式规范，必须先分级。

建议 Skill 输出每条规则时带：

```text
confidence: high / medium / low
evidence_count: 证据数量
source_files: 证据文件
risk_level: high / medium / low
review_required: true / false
```

例如：

```json
{
  "rule_id": "STD-BE-JAVA-P0-001",
  "title": "Controller 不得写业务逻辑",
  "confidence": "high",
  "evidence_count": 8,
  "source_files": [
    "order/OrderController.java",
    "trade/TradeController.java"
  ],
  "review_required": true
}
```

Skill 生成结果进入正式规范前，必须人工确认：

```text
high：可优先合入，但仍需负责人确认
medium：需要端负责人判断
low：只能进入待确认，不得进入 P0
```

# 七、防止“看起来完整但难落地”的 10 条约束

可以作为规范编写原则写进仓库。

```text
1. 没有代码证据的规则，不进入 P0。
2. 没有 AI 生成代码要求的规则，不进入 AI Rules。
3. 没有 Review 检查项的规则，不进入强制规范。
4. 只讲原则、不讲边界的规则，必须重写。
5. 只有正例、没有禁止写法的规则，必须补充反例。
6. 只是行业通用建议、但项目没有实践的规则，标记为 P2 或待确认。
7. 历史代码中存在的写法，不默认视为推荐规范。
8. 每个端 V1 P0 规则控制在 10 条左右。
9. AI Rules 必须短于人读版，不得复制整篇规范。
10. 所有规则必须能被真实需求试点验证。
```

# 八、建立文档质量验收标准

每份规范文档发布前，按下面清单验收。

## 1. 结构验收

```text
是否有 Front Matter？
是否有适用范围？
是否有技术栈说明？
是否有分层职责？
是否有核心规则？
是否有 AI 生成代码要求？
是否有 Code Review Checklist？
是否有待确认事项？
```

## 2. 规则验收

```text
每条核心规则是否有 Rule ID？
每条 P0 是否有推荐写法？
每条 P0 是否有禁止写法？
每条 P0 是否有 AI 要求？
每条 P0 是否有 Review 检查项？
规则级别是否合理？
```

## 3. 证据验收

```text
是否标注正例代码路径？
是否标注反例代码路径？
是否区分推荐模式和历史兼容模式？
是否存在无证据强规则？
```

## 4. AI 验收

```text
AI 能否根据文档生成正确目录结构？
AI 能否根据文档遵守分层？
AI 能否引用 Rule ID 自检？
AI 是否仍然生成文档明确禁止的代码？
```

## 5. Review 验收

```text
Reviewer 是否能用规则指出问题？
Checklist 是否可判断？
是否能减少主观争论？
是否能沉淀高频 Review 问题？
```

# 九、质量闭环机制

文档质量不是一次写好，而是持续进化。

建议建立这个闭环：

```text
真实代码 / AI 出错 / Review 问题
        ↓
提炼问题模式
        ↓
补充或修改规则
        ↓
更新 AI Rules
        ↓
更新 Review Checklist
        ↓
真实需求试点
        ↓
沉淀为正式规范
```

每次 AI 出错，不要只改 Prompt。

要追问：

```text
这是不是规范没写清？
是不是 AI Rules 不够硬？
是不是缺少反例？
是不是缺少模块边界说明？
是不是规则没有进入 llms.txt / rules-index.json？
```

# 十、最终建议的质量保障体系

可以把质量保障设计成四层。

```text
第一层：生成质量
- 从真实代码萃取
- 不凭空编写
- 保留证据

第二层：规则质量
- Rule ID
- 推荐写法
- 禁止写法
- AI 要求
- Review 检查项

第三层：评审质量
- 端负责人 Review
- 架构负责人 Review
- AI 试点验证

第四层：迭代质量
- AI 出错反哺
- Review 高频问题反哺
- 规则版本化
- rules-index.json 经人工合入后更新
```

---

# 十一、一句话总结

要保障文档质量，核心不是让文档“完整”，而是让每条规范都满足：

> **有真实代码证据、能被 AI 执行、能被 Review 检查、能通过真实需求验证。**

最终你们要管控的不是文档页数，而是每条规则的质量。

可以定一个硬标准：

```text
凡是不能指导 AI 写代码、不能指导 Reviewer 检查、不能追溯到团队实践的内容，都不进入第一版正式规范。
```
