# APP UI 组件规范

## 1. 规范定位

UI 组件规范用于约束 Android 和 iOS 平台层的页面组件、通用组件、状态展示、多语言、主题和多展业地 UI 差异。UI 层应保持轻量，只负责渲染、交互和状态展示，不承载可跨端复用的业务规则。

## 2. UI 层职责

UI 层负责：

- 页面布局。
- 用户交互。
- 状态订阅。
- 状态渲染。
- 多语言文案展示。
- 主题和样式展示。
- 平台交互细节。

UI 层不负责：

- 网络请求。
- 数据库访问。
- 缓存策略。
- DTO 字段兼容。
- 交易、账户、订单、行情等核心业务规则。
- 多展业地业务规则判断。

## 3. 组件类型

| 组件类型 | 示例 | 规则 |
| --- | --- | --- |
| 基础组件 | Button、Input、Dialog、Toast | 保持平台一致交互 |
| 业务组件 | 股票卡片、订单状态、账户资产 | 只消费 Domain Model 或 UI State |
| 容器组件 | 列表、分页、Tab、筛选器 | 不承载复杂业务规则 |
| 状态组件 | Loading、Error、Empty、Retry | 必须统一复用 |
| 展业地组件 | 主题化首页、合规提示 | 差异通过配置或策略注入 |

## 4. 状态展示规则

强制规则：

1. 页面必须处理 loading、error、empty、success。
2. 错误态必须提供用户可理解的提示。
3. 可重试错误必须提供重试入口。
4. 空态必须说明当前状态，不得使用空白页面替代。
5. 成功态必须处理数据缺省字段。

推荐规则：

1. 列表页应区分首次加载、下拉刷新和加载更多。
2. 详情页应支持骨架屏或占位状态。
3. 高频行情页面应避免频繁触发布局重排。
4. 交易和账户页面应提供明确的异常兜底。

## 5. 多语言规则

强制规则：

1. UI 文案必须走多语言资源，不得硬编码。
2. 后端返回文案进入 UI 前必须确认是否允许直接展示。
3. 错误文案应优先通过统一错误模型映射。
4. 新增展业地必须确认语言列表和默认语言。

推荐规则：

1. 文案 key 命名应体现模块和场景。
2. 多语言文案应避免依赖固定长度。
3. 金额、日期、数字和市场代码应符合展业地格式。

## 6. 主题规则

强制规则：

1. 颜色、字体、间距、圆角等样式应走主题或组件 token。
2. 不得在页面中硬编码展业地主题差异。
3. 新增主题必须覆盖默认态、禁用态、选中态、错误态。
4. 交易、行情等高频页面应保证颜色语义稳定。

推荐规则：

1. 多展业地 UI 差异优先通过主题 token 解决。
2. 复杂组件应提供明确的视觉状态枚举。
3. 图标、图片、静态资源应支持展业地替换。

## 7. 组件复用规则

强制规则：

1. 新增组件前必须检查是否已有同类组件。
2. 业务组件不得直接发起网络请求。
3. 业务组件不得直接依赖后端 DTO。
4. 通用组件不得依赖具体业务模块。

推荐规则：

1. 可跨页面复用的组件应沉淀到组件模块。
2. 组件 API 应表达展示语义，而不是暴露底层 DTO 字段。
3. 组件应尽量由外部注入状态和事件回调。

## 8. AI 生成规则

AI 生成 UI 代码时必须遵守：

1. 页面只负责渲染和交互转发。
2. 不允许 UI 直接访问网络。
3. 不允许 UI 直接使用后端 DTO。
4. 不允许在 UI 层硬编码展业地判断。
5. 必须处理 loading、error、empty、success。
6. 文案必须走多语言资源。
7. 颜色、字号、间距必须复用现有主题或组件体系。
8. 新组件必须先说明为什么不能复用已有组件。

## 9. Review 检查项

- UI 是否保持轻量。
- 是否完整处理页面状态。
- 是否存在硬编码文案。
- 是否存在硬编码颜色或主题差异。
- 是否直接依赖 DTO。
- 是否直接发起网络请求。
- 是否重复创建已有组件。
- 多展业地 UI 差异是否通过配置、主题或组件契约解决。
