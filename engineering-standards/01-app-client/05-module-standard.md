# APP 模块化开发规范

## 1. 模块化目标

APP 模块化的目标是让核心业务能力可复用、可替换、可测试，并支持多展业地按配置组合能力。

模块化必须服务于以下目标：

1. 核心业务逻辑优先下沉 KMP。
2. 平台层只保留状态管理、UI 渲染和平台能力适配。
3. 数据访问统一走 Repository 和 HSDataCenterKit。
4. 多展业地差异通过配置、策略或 DI 隔离。
5. 模块之间依赖清晰，避免横向随意调用。

## 2. 模块类型

| 模块类型 | 示例 | 说明 |
| --- | --- | --- |
| 核心业务模块 | 交易、行情、账户、用户 | 优先 KMP 复用 |
| 通用能力模块 | 搜索、推送、配置更新 | 可跨 APP 复用 |
| 基础设施模块 | 网络、缓存、数据库、日志 | 双端统一封装 |
| UI 组件模块 | 通用列表、弹窗、按钮、表单 | 保持交互一致 |
| 展业地适配模块 | KAZ、本地市场配置 | 配置化、策略化 |

## 3. 模块边界规则

强制规则：

1. 模块必须明确自身职责和外部依赖。
2. 模块不得直接访问其他模块的内部实现。
3. UI 模块不得直接调用底层网络。
4. 业务模块不得直接依赖具体页面实现。
5. 多展业地差异不得污染模块主流程。
6. 新增模块必须说明 KMP 共享边界。

推荐规则：

1. 模块之间通过接口、UseCase、Repository 或路由契约交互。
2. 可复用能力优先沉淀为 shared module 或 platform component。
3. 历史模块改造时优先抽离数据访问和核心业务规则。

## 5. 模块依赖规则

推荐依赖方向：

```text
App Shell
    ↓
Feature Module
    ↓
KMP UseCase / Repository
    ↓
HSDataCenterKit
    ↓
Infrastructure
```

禁止依赖：

- Feature Module 直接依赖底层网络实现。
- UI 组件模块依赖具体业务模块。
- KMP commonMain 依赖 Android 或 iOS 页面实现。
- 展业地适配模块反向污染基础业务模块。

## 6. 业务模块规范

业务模块必须明确：

1. 模块职责。
2. 核心业务流程。
3. 核心 Domain Model。
4. KMP 共享能力。
5. Android 平台适配点。
6. iOS 平台适配点。
7. 数据访问入口。
8. 缓存策略。
9. 错误处理。
10. 埋点与日志。
11. 多展业地差异。
12. AI 生成代码注意事项。

## 7. 通用能力模块规范

搜索、推送、配置更新等通用能力模块应满足：

1. 能被不同 APP 组合复用。
2. 对外暴露稳定接口或路由契约。
3. 不直接依赖单一展业地。
4. 差异化能力通过配置或策略注入。
5. 数据访问和缓存策略清晰。

## 8. 基础设施模块规范

网络、缓存、数据库、日志、配置、多语言、主题等基础设施模块应满足：

1. 对上层隐藏底层实现细节。
2. 提供统一错误、日志和监控入口。
3. 不依赖具体业务页面。
4. 不暴露可被 UI 层随意调用的底层接口。
5. 变更前必须评估影响范围。

## 9. AI 生成规则

AI 生成模块代码前必须判断：

1. 当前需求属于已有模块还是新模块。
2. 是否已有可复用 UseCase、Repository、组件或配置。
3. 哪些逻辑应进入 KMP。
4. 哪些逻辑应留在 Android 或 iOS 平台层。
5. 是否影响多展业地。
6. 是否需要新增模块标准文档。

禁止 AI 生成：

- 重复 Repository。
- 重复 UseCase。
- 重复 UI 组件。
- 绕过模块边界的跨模块调用。
- 为单一展业地硬编码模块逻辑。

## 10. Review 检查项

- 模块职责是否清晰。
- 依赖方向是否正确。
- 是否复用已有模块能力。
- 是否存在重复业务规则。
- 是否明确 KMP 共享边界。
- 是否绕过 HSDataCenterKit。
- 是否存在展业地硬编码。
- 是否补充模块级测试和文档。
